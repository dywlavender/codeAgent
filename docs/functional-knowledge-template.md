# 功能知识正文模板

> 版本：V1
>
> 用途：生成和审核一项业务功能的可读知识。
>
> 说明：本文是面向人阅读的知识正文模板。证据 ID、来源版本、置信度、审核状态等由系统自动维护，不要求开发人员手工填写。

## 使用边界

- 一份知识对应一个业务功能，不对应整个项目，也不强制对应单个类或接口。
- 入口类、方法、批任务和消息消费者由代码分析自动发现；人工只负责确认归属。
- 需求说明业务意图，代码说明当前实现，人工说明补充真实业务语义。
- 需求与代码不一致时保留差异，不自动选择一方作为最终结论。
- 没有足够证据的内容进入“待确认问题”，不写成确定事实。

## 系统自动维护的附加信息

以下内容不放在正文中，由系统绑定到对应的段落或条目：

- 需求来源及版本；
- 代码仓库、分支或代码快照；
- 人工补充说明的来源标识；
- 知识标签的类型、标准标识和别名；
- 每条结论对应的 Evidence；
- 知识版本、审核状态和更新时间；
- 冲突记录、待确认项和证据覆盖情况。

页面默认展示正文，点击“依据”时再展开需求原文、类、方法、批任务或其他证据。

## 知识标签规则

“知识标签”是知识图的连接锚点，不是随意填写的关键词。标签由系统从代码、需求和人工补充中归纳，管理员只在标签含义不准确时进行确认或修正。

每个标签至少包含以下信息：

```text
标签类型：业务域 / 业务对象 / 业务流程 / 业务场景 / 关联系统
标签名称：页面展示名称
标准标识：系统用于归并同义词的稳定标识
别名：可选的历史名称或代码名称
```

例如“提款申请”“提款申报”等名称如果确认属于同一个业务概念，应归并到同一个标准标识下。知识图可以据此连接功能、场景、需求和代码证据；仅有相同标签时只能作为关联候选，不能直接当作确定关系。

## 人工补充原则

人工不需要完整填写以上模板，通常只需要补充一段说明：

```text
这个功能大概解决什么问题；有哪些特殊业务规则；哪些代码或批任务可能属于它。
```

其余内容由系统根据代码事实和需求 Digest 生成草稿，再由管理员确认、修改或驳回。

## 冲突展示方式

当需求与代码不一致时，使用以下形式展示：

```text
需求期望：还款方式只能是 A
当前实现：代码同时支持 A、B
处理状态：待确认
```

冲突确认后，系统才可以将处理结果写入下一版已发布功能知识。
