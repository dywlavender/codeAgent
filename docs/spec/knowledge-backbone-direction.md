## 1. 知识主干的定义

知识主干是供大模型理解项目并持续指导代码调查的项目认知地图。它组织项目整体认识、业务术语、系统职责、完整的业务流程、关键业务关系和稳定的入口类等知识，让模型从更有依据的检索假设出发，在读取代码、获得线索、继续检索的过程中少走弯路。

它的作用贯穿调查全过程，不能收窄成“业务问题到代码入口的映射”。模型既需要知道从哪里开始，也需要知道当前调查处于业务流的哪一段、还缺少哪些关键环节，以及何时应该转向另一个系统或异步入口。

这里的“完整业务流”指在所描述业务范围内，覆盖主要阶段、参与系统、关键分支、异步衔接和必要的异常／补偿路径。完整性体现在业务层，不要求复制全部方法调用、字段和实现分支；尚未覆盖的部分应明确标出，不能把局部流程当成全貌。

## 2. 知识主干的内容与作用

| 内容 | 帮助模型解决的问题 |
| --- | --- |
| 项目整体结构、系统和应用职责 | 这是什么项目，业务由哪些系统协作完成，应在哪些仓库调查 |
| 业务术语、别名、历史名称、代码代号 | 用户的业务说法在代码中如何表达，第一次和后续检索应该用哪些词 |
| 业务全流程及关键分支、异步衔接 | 当前证据对应哪个阶段，前后还有什么，是否遗漏关键环节 |
| 业务能力、规则及有来源的业务背景 | 某段实现承担什么业务职责，为什么需要调查相关分支 |
| 稳定的页面、入口类、任务或消费者 | 从哪里进入源码，什么时候需要切换调查入口 |
| 业务对象、流程、系统、事件之间的明确关系 | 根据已获得的线索，下一步应扩展到哪些相关业务和实现 |

预期减少三类弯路：业务词与代码词不匹配；在错误系统中持续搜索；找到局部实现就过早认为业务调查已经完成。

## 3. 词云（知识图谱）的定义与作用

用户讨论中的“词云”按具有业务语义关系的知识图谱理解，不能实现为只展示词频、字号和关键词的普通词云。

知识图谱是知识主干中概念及其关系的组织与呈现方式。节点可以包括术语、系统、应用、业务能力、流程、规则、事件和入口；关系必须具有明确含义，例如：业务名称对应代码代号、系统负责某个阶段、事件触发后续流程、流程具有某个调查入口。

图谱用于帮助人和模型理解、检索和沿关系扩展项目知识。对模型而言，关键是能够取得并理解相关节点及关系；对用户而言，关键是能看懂业务上下文和调查方向。图形展示只是其中一种形式，画出更多节点和连线不等于问答能力已经提高。

知识图谱与业务文档应表达一致的业务知识。图谱是主干的组织与使用方式之一，不应成为与原文各自维护、互相矛盾的另一套事实。

## 4. 与大模型代码调查的关系

目标过程如下，表示信息如何帮助调查，不要求每道题强制执行固定步骤：

用户问题 → 借助项目认知和相关业务流形成检索假设 → 搜索入口并读取源码 → 根据源码线索与业务关系继续调查 → 确认当前实现、覆盖范围与尚未确认的部分。

主干提供背景、方向和业务覆盖参照，源码确认当前实现。模型应能用源码修正或推翻主干中的假设；业务约定与当前实现不一致时，应分别说明。

模型也可能通过 README、目录结构等资料自行建立项目认识。因此，主干的增益应相对于“已有项目资料和代码均可正常使用”的调查过程衡量，不能把对照组已有的背景信息刻意删去。

## 5. 后续整改原则

1. 优先让知识主干实际参与模型的项目理解和持续调查，不能停留在管理员维护和独立图谱浏览。
2. 同时保留整体认知与按需展开的能力，避免只给零散入口，也避免每题无差别塞入全部知识。
3. 内容优先补充项目特有术语、系统边界、跨系统业务流、异步关系和稳定入口。可以从源码直接确认的实现细节不应大量重复维护。
4. 保留必要的来源、适用范围和更新信息，使错误或过时知识可以定位和修正；维护负担要与实际收益一起评估。
5. 不要求每题必须读主干，也不强制沿既定流程调查到底。模型根据问题相关性和源码线索决定调查范围。
6. 页面应帮助用户理解业务关系以及这些知识如何关联当前调查。区分“资料可用”“实际读取过”和“对调查有帮助”，不能把读取次数当成贡献证明。
7. 本文不预设图数据库、检索算法、工具接口或固定 Agent 工作流。技术方案围绕上述作用选择；不能因为已有结构化模型，就默认其成本必然值得。

## 6. 判断是否有效

核心验证问题：同一道真实业务问题，提供主干后，模型能否更早找到正确业务范围，减少无关探索，并更少遗漏关键流程。

重点观察正确系统与入口的定位、业务术语消歧、关键业务环节覆盖、源码结论正确性及无关搜索；耗时、工具调用和上下文消耗作为辅助指标，同时考虑知识维护成本。

有主干时，模型可能因发现原先遗漏的异步步骤而读取更多文件。这可能是调查质量提升，不能仅因调用次数增加就判断失败；同样，少查几个文件也不能直接证明成功。

以真实且存在术语差异、跨系统或异步关系的问题验证，并保留普通代码题作为对照。需要区分“业务文档带来的收益”与“结构化关系在文档基础上的额外收益”。现有小示例的结果不能直接外推到真实老项目。

## 8. 复杂项目的验证假设

用户提出：复杂项目可能比当前简单示例更能体现知识主干的作用。这是合理但尚未验证的假设。应按业务词与代码词差异、跨系统职责、关键异步衔接与流程分支等实际调查困难分层验证，不仅按代码行数或仓库数量判断。

复杂项目也会增加知识过时、关系冲突和上下文负担。因此保持“简短项目总览＋按需业务流程”的组织方式，验证模型是否减少无关探索和关键遗漏。普通代码题继续保留，不能以复杂项目可能有效为由忽略当前无增益的结果。

持续回归入口见[知识主干自动对照验证](knowledge-backbone-automation.md)。自动报告须同时展示质量与成本，模型评分标为初评，不以成功运行或知识读取次数判定有效。

## 10. AST 对照（2026-09-08）

用户要求继续真实验证并实现AST对照。增加独立AST、相同业务总览＋AST两种处理，区分代码结构导航和人工业务流程主干的贡献；保留正常资料，按实际命令和工具轨迹区分注入、读取与收益。AST不等同业务知识图谱。生成成本与答题成本分列，旧无结构导航批次与新版分开解释。见[AST对照方案](../records/2026-09/ast-comparison-20260908.md)。

本轮产品流程进一步约定：AST 是独立的结构资料版本，由用户在 AST 管理页手动生成、查看和重新生成。项目启动、进入页面、选择 AST 问答模式和启动实验都不得隐式触发生成；源码变化只将版本标记为待更新。主对话和三组实验必须引用同一套已生成 AST 资料，实验记录保存实际版本，AST 生成耗时与答题耗时分开统计。AST 模式不提供人工业务主干，参考答案和评分要点只进入评审环节，不进入三组答题上下文。

### 10.1 结构资料能力补充（2026-11-13）

在保持上述手动生成、版本冻结、永不隐式生成约定的前提下，补齐结构资料四项基础能力：AST 文档条目（类型与方法清单）渲染全限定名，作为跨资料可解析锚点；索引在原始 CALL／INHERITS_DECL 事实之上维护确定性解析层，只有唯一解析到仓库内符号的调用与继承才成为 CALLS／INHERITS 事实，解析不到直接省略，不猜（父类型后续出现时下一次全量同步收敛）；AST 源码指纹改为内容哈希聚合（size+mtime 快路径缓存），touch 不再误报待更新，旧版本按旧算法比较直至重新生成；服务重启遗留的 generating 状态在下一次构造时标记为失败并说明原因。每个 AST 版本目录同时保留渲染文档与 index.db 符号库，供后续可编程消费；md 视图、分片与上下文预算约定不变。检索后端与跨域适配器仍属后续阶段，当前不把 AST 索引库当作答案证据，也不把它当作第二套生产检索默认。

## 11. 知识体系重构方案（2026-09-08，资料边界）

前述第 1—10 节记录了此前对“大知识主干”和 AST 对照的讨论及验证结果；截至本节确认，新的实现和验收以本节为准。原因是多轮真实问答没有证明当前大块业务基线稳定带来收益，且其中存在源码重复、过时和维护成本。不能把旧实验中“读取了资料”解释为新方案已经有效。

### 11.1 四类资料的边界

| 资料 | 作用 | 不应承担的内容 |
| --- | --- | --- |
| 源码和 README | 确认当前实现、技术调用关系和现有项目背景 | 不因需求或业务文档而被替代 |
| 需求原文 | 说明提出过的目标、约束和验收语义 | 不代表已经实现 |
| 业务补充知识 | 记录源码难以可靠推断的项目特有语义、术语歧义、系统边界、隐式跨系统关系和例外 | 方法链、URL、类名、字段、行号、可由源码直接确认的当前实现 |
| 自动代码地图 | 从同步／索引／结构解析结果中提供仓库、目录、文件和符号定位 | 业务结论、正确性证明或人工业务主干 |

业务补充知识不是“入口映射的别名”，但也不再追求复制完整业务流程。只有确实存在语义缺口时才维护；每条内容应有依据、适用范围和更新信息。知识图谱先作为管理和可视化能力保留，是否进入问答必须由后续收益验证决定。

### 11.2 运行时约定

2026-11-02 用户确认主问答组合使用资料：默认 `mode=combined`，源码、README、需求、业务补充知识、已有自动代码地图及可用的手动 AST 版本同时可检索，按问题需要读取。主问答页取消互斥资料选择；AST 未生成、待更新、生成中或生成失败时继续使用其余资料，不自动生成或更新。AST 与自动代码地图各自挂载，来源仍可区分，具体实现结论返回源码核实。

旧无主干／有主干／AST 模式仅保留历史兼容与显式对照：无主干使用正常项目资料；有主干增加业务补充；AST 组只增加结构资料，不额外提供业务补充。独立实验继续固定各组资料并记录版本，不因主问答默认改变而改写旧批次。项目索引和代码地图只用于缩小搜索范围。

运行时不再把旧的 `project-overview.md` 全文无差别注入每一题。可以保留简短的 `project-index.md` 作为资料索引，但业务文档和结构分片均按问题需要读取。历史单工程配置可通过兼容别名读取，新的注册工程使用 `knowledge/business-context/` 和 `knowledge/generated-code-map/`。

### 11.3 资料迁移和评测顺序

旧基线先分类为：源码或 README 已有内容、需求重复内容、真正的业务语义增量。前两类不继续扩写，第三类迁移到业务补充知识；不确定的内容保留为待核查项，不直接当作事实。自动代码地图沿用现有索引／结构产物，不能因为生成了目录就宣称问答收益。

重构后的评测计划使用五组：正常资料基线、旧基线、自动代码地图、业务补充知识、自动代码地图＋业务补充知识。题目按纯代码、代码定位、业务语义、术语不一致和隐式跨系统关系分层；质量、遗漏、无关探索、耗时、调用成本和资料维护成本分开记录。该五组协议在现有三组历史记录之上新增，不能覆盖旧批次，也不能用不同题目的平均分直接比较。

### 13.1 答题事实与结论范围

主问答默认 `BUSINESS_CODE_AGENT_ANSWER_MODE=plain`，`facts` 为可选实验模式。事实模式调查阶段仍按需搜索，最后一次无工具答题只整理本轮实际交付的原文：接口返回字段、单一展示映射、页面实际使用、业务行为、需求目标和业务约定分别记录。相关层次按问题选取，不把所有层次变成每题必查的固定清单。模型提出事实和建议，程序检查来源、行号、可选逐字引文、字段路径分段和声明范围，再输出答案；不直接放行未经检查的自由结论。2026-10-31 两次真实固定证据复验仍有对象归属和引用遗漏，因此尚未通过默认启用验收。

程序可纠正“已观察到返回字段却判为不支持”等有限矛盾，并阻止用模型标记的展示事实去证明整个接口缺数据；未取得的字段和页面消费证据只能记为未确认。建议新增的字段如已确认返回，先提示复用；建议依赖的事实有未通过项时不能静默忽略该项后继续建议。需求与导航不作为当前实现依据。同一文件分次读取的已交付行可共同作为引用，缺失行不能从磁盘暗中补入。字段分段都出现仍不能证明它们的嵌套或跨系统绑定；模型也可能错误分配范围。目前页面消费关系不由模型的 ui 标签直接判定，业务语义解释只标为原文解读。所需字段是否完整、资源归属和改动收益仍需要独立源码复核，不得把这一检查称为通用语义证明或业务链路完整性保证。

验证先重放旧运行实际交付的相同原文，关闭搜索，不注入旧答案和参考标注，并分别记录模型原始结构结果与程序输出。固定证据改善只能说明答题阶段的效果；完整 Agent 的搜索质量、补查能力和新保留题的泛化效果需另行验证。来源格式失败时输出未确认结论，不再消耗额外模型调用自动重试。

### 13.2 工具与调查状态

文件工具的递归 Glob 支持 `**` 跨零层或多层目录，目录发现用 `kind=directories`；Grep 默认区分大小写，提供显式忽略大小写和整词参数。不能把工具匹配错误解释成资料不存在。工程职责导航复用配置中的系统／应用／仓库归属，按当前工程与授权仓库过滤；它只用于选择范围，不证明接口连接或页面实现。

`BUSINESS_CODE_AGENT_WORKFLOW=basic` 提供文件工具、职责导航和搜索状态交接。`tracked` 与 `coordinated` 提供 Investigation，按本题需要记录对象文件、关键待办、端点引用和资料缺口。明确 next_read 后，程序在下一次模型请求前补读。同批原文到达后检查任务更新。关系任务需不同文件／符号端点的引用，页面任务需已登记前端的源码引用。当前默认调度见第 13.3 节。

模型提交答案时，有可执行的程序补查才恢复调查。关键事项仍开放且已无具体补查时，程序使用已取得原文进入一次无工具答题，保留未确认事项。不可查资料可登记为 unavailable 并说明原因。一次真实回归补读了客户端和渠道 Controller，仍有字段断言错误与待办未更新。

逐轮快照保存交给 LangChain 适配器的公开消息、工具定义、公开响应、用量和调查状态，不记录模型私有思考或认证信息。程序补读与模型选择的调用区分来源。快照是供应商序列化前的记录，不冒称 HTTP 原始报文。完整 Agent、固定证据与本地模拟流程分别验证和报告。

## 14. 契约与返回字段索引（2026-10-31，用户确认）

先落实窄范围的结构中间层：Spring HTTP 端点、RestClient 及配置绑定、方法委托、Map／可支持 DTO 的返回字段与对象透传关系。复用工程内 SQLite，提供入口定位、契约连接和返回字段查询；Kafka／GraphQL 与更广的业务语义图按实际缺口扩展。业务能力作为入口，源码符号、契约、字段与条件作为证据，不把整个能力复制成大块文字。

索引必须显式准备／更新，查询不隐式解析 AST。每条关系保留两端身份、源码位置、连接依据与索引版本；不支持的表达式、缺少配置的调用、歧义和过期关系必须保留为未解析，不能因唯一候选就推断正确。多仓库连接限定在当前 ProjectContext，未索引不等于没有关系。

查询输出小型证据包，包含已有字段、生产与透传路径、展示投影、相应源码和缺口。由具体未解析关系生成补查任务，读取结果自动归属该关系，避免再依赖模型自觉维护宽泛计划。补读当前源码不会暗中重建结构索引，过期的结构关系不能据此恢复为确定。

最终回答对接口数据、展示转换和页面消费分别给出结论；已确认的字段事实不由模型自由改写为不存在。模型解释业务含义仍需原文依据，不将有限的结构解析称为任意业务语义证明。实现与收益分别验收，使用正常文件工具、增加契约索引、契约索引加业务语义的同模型同预算对照，不删减正常资料，不把结构定位成绩当问答正确率。实现前的方案与来源见契约图借鉴记录；第一阶段实验未通过前不默认切换生产链路。

契约实验提供独立开关和两个答题方式：`CONTRACTS=on` 增加契约工具，保留 `plain` 自由答题作为检索消融；`ANSWER_MODE=contracts` 则将结构事实交给程序渲染，并接纳模型引用已交付分支编号的业务解释。返回成员关联真实 getter／setter 与源码 if、try/catch 写入点，问题明确涉及状态、失败、区分、条件或改动时，在字段核对后由程序补查；字段清单题不强制展开。词项规则只是有限的触发器，模型仍可主动补查未触发的问题。

解释必须有对应返回字段与分支原文，改动按复用、投影、补查字段与消费端核对给出条件选项。映射输入不足以支持所需细分时说明依赖；未核对消费者不承诺单点收益或排序。已读原文按行号合并去重，空缺和冲突保留，不能把结构证据与全文重复注入造成的成本当收益。局部写入点不是完整状态机、请求轨迹或全部业务语义证明；需同时记录避免的误判与尚未回答的条件。更广的语义实体链接、事件与页面消费证明尚未由此实现。
