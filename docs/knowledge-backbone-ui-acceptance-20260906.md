# 效果验证页面验收记录

日期：2026-09-06。验收对象：当前工作区新增效果验证页面及 evaluation 后台模块。依据：知识主干效果验证页面方案。

**结论：暂不通过完整验收。主要功能已经接通，但发现 4 个已复现的功能问题。** 本轮仅验收，没有修改业务实现。

## 已通过与范围

- 本机 8082 的实际页面能够打开既有批次，显示质量／成本、分母、评分来源与逐题结果；未把运行完成显示为主干有效。
- 评测服务测试 10 项、HTTP 接口测试 3 项、评分与汇总测试 4 项、模型 runtime 测试 7 项、前端现有测试 8 项，共 32 项通过；前端生产构建通过。
- HTTP 测试最初受沙箱本地监听限制，随后在允许本地监听的环境完成并通过；不计为产品失败。
- 另在 8089 启动独立验收环境，使用临时项目与模拟模型复现交互；不改动现有题库或评分记录，不追加真实模型调用。本轮验证功能正确性，不重新衡量知识主干收益。
- 模拟评分失败时，答案保持完成、质量标待评，未将失败按零分处理；模型评分与复核汇总分母分离的现有接口测试通过。

## 1. P1：停止操作无法取消正在执行的初评

位置：`business_code_agent/evaluation/harness.py:119`，以及调用 judge_answer 的答题／重评路径。

复现：让答题完成，初评进入可阻塞的模拟 runtime 后执行 service.cancel。初评 runtime 收到的 cancel_check 为 None；停止后活动调用继续等待，直到主动释放模拟 runtime 才结束。实际 runtime 本身的取消测试已通过，缺陷在评测链路没有把取消信号传下去。

影响：用户停止批次后，初评模型调用仍会继续运行和消耗；不能满足“活动调用取消”的验收要求。

修复要求：judge_answer 接收并传递批次取消检查；首次初评和重新初评均接入；取消结果与评分格式错误区分。补充“已进入初评后停止”的测试，不能只测试答题期间取消。

## 2. P2：重新初评后页面不更新，也无法正常跟踪重评进度

位置：`frontend/src/pages/EvaluationPage.jsx:918`、`:950`、`:980`；后台重评使用独立的 rejudge.status。

复现：独立验收批次原有两份“初评失败”，从页面点击重新初评并确认。后台 state 已为 rejudge.completed，评分可用 2/2；页面仍显示初评失败 2、可用 0，未主动刷新。

原因：runAction 忽略返回值，也没有重新获取详情；轮询仅看 detail.status 是否 running/cancelling，而重评时原批次仍为 completed。因此当前页面没有跟随重评的状态变化。

修复要求：首次启动重评后立即更新详情，活动判断和停止入口覆盖 rejudge 状态，重评结束刷新摘要与历史。补充实际页面交互测试。

## 3. P2：重新初评重置用户复核状态，导致页面与汇总矛盾

位置：`business_code_agent/evaluation/service.py:540`，`_run_rejudge` 复用 `_apply_result`。

复现：对两份答案保存完整复核，reviewCoverage.reviewed 为 2；执行重新初评后，该值变为 0。复核文件仍然存在，复核视图 qualityBlocks 仍为 1。

影响：页面将已有复核显示为未复核，但汇总继续使用复核记录。用户可能重复复核，且无法信任覆盖数。这里是复核状态被重置，不是原复核文件被删除。

修复要求：重新初评只更新模型评分状态；复核状态应根据独立复核记录计算或保留。测试先保存两侧复核、再重评、确认覆盖数和修订不变。

## 4. P2：配置页的启动失败提示不可见

位置：`frontend/src/pages/EvaluationPage.jsx:973`、`:1030`、`:1032`。

复现：独立配置页显示就绪后，使验收源码仓库暂时不可用，点击开始。后台就绪校验失败，按钮从 loading 恢复；页面没有错误提示，仍保留之前的就绪信息。验收后已恢复测试仓库。

原因：start 将错误写入 actionError，但该状态仅传入 BatchView；尚未创建批次时实际渲染 ConfigCard，错误没有渲染出口。管理员启动被拒绝或题库校验失败也进入同一分支。

修复要求：在配置和批次视图共同区域显示操作错误，或显式传给 ConfigCard；保留所选设置，给出可理解的错误原因。

## 其他与方案的差距

以下通过代码检查确认，尚未进行复杂仓库性能实测，不与上述 4 项复现问题混为一谈：

- freeze_batch 在启动 HTTP 请求内同步复制源码，持有服务锁；资料准备完成后才创建任务状态和后台线程。因此尚未实现方案中“立即创建任务并显示准备资料进度”，大项目复制期间也不能通过批次接口停止。见 service.py 的 start／freeze_batch 调用。
- 初次答题状态直到初评完成才通过 on_finish 更新；尚没有答题结束、初评开始的独立进度通知。失败初评的“已结束”计数也只取成功初评数，页面可出现“已结束 0/2，初评失败 2”。
- 历史“按相同设置重跑”未传原 caseIds，曾只选部分问题的批次会重新运行整套题库。

## 整改后复验

优先修复上述 4 项，再补齐资料准备和阶段状态。复验需同时覆盖页面交互与后台行为，至少验证：初评期间停止；重评实时更新；重评保留复核状态；启动失败有提示。无需为这些状态测试重复调用真实模型。

本地复现材料保存在 `.data/acceptance-evaluation/`，其中 `probe.py` 验证取消信号与复核状态重置，`serve.py` 提供独立页面验收环境。它们是验收材料，不是生产实现。
