# Agent 调查轨迹复盘（2026-10-31）

## 结论与分析边界

本次逐轮核对两轮共四份 Agent 事件、两份实际交付原文、最终回答、两次固定证据结构输出及当前运行时代码，没有新增模型调用。此前核查主要集中在最终答案和三个标注证据组是否已读，未充分分析搜索行为、调用连接与收尾状态传递；优先增加尾部事实校验的顺序不够合理。

已确认的问题分布在工具语义、调查方向、调用连接、收尾状态和答案综合，不能统称为模型能力不足，也不能只用更换检索算法解释。第一轮预算耗尽是已修复的收尾问题，第二轮已有正文后的证据使用错误仍存在，二者不能混为一谈。

日志包含轮次状态、工具参数、工具结果和最终答案，未保存完整逐轮请求快照或模型随工具调用给出的公开规划文本；历史评测临时工作区也未随结果持久化。可以定位可观察的断点，不能断言模型究竟在哪一轮形成了错误假设。初轮混合检索事件正文还被截为 10,000 字符，已不是完整 JSON；这证明审计记录不完整，不能据此断言模型当时也收到了截断输入。第二轮保存了完整正文。

复盘为助手核对，`humanReviewed=false`。模型设置为 qwen3.8-27b、非思考、每版最多八次调用；没有同题预算或思考开关的单变量实验，不能推断换模型、加预算或开思考一定解决问题。

## 已复现的工具问题

`query/langchain_agent/files.py:100` 使用 `PurePosixPath.match`。本机用真实 SourceFiles 的临时目录复现：

```text
已有文件：knowledge/business-context/terminology.md
Glob knowledge/business-context/**/* → []
Glob knowledge/business-context/*    → [terminology.md]
```

当前匹配实现没有提供通常递归 glob 中 `**` 可跨零层目录的语义。两份有效运行因此未通过这次目录定位取得业务资料；文件版后续没有 Read 补充知识，混合版通过 SearchCode 取得部分知识。该缺陷不能被解释为资料目录为空或模型不愿读取。

此前工具测试覆盖范围限制、读取行数和简单模式匹配，没有覆盖轨迹中的这条真实目录模式。77 项相关测试通过不等于常用检索动作已获验收。

`files.py:109` 将所有 Grep 固定为忽略大小写，工具参数不提供切换。本机复现 `PROCESSING` 同时命中枚举和 `Data processing`。文件版第 7 轮的通用英文文本就是这种噪声，结果还按文件遍历顺序先到先收，达到 30 条即截断。需要改进大小写／整词控制和范围定位，不能把所有问题归给模型选词。

第一轮文件版另有猜错 `middle-service-repo`、使用 `repos/*` 寻找目录的行为；目录清单与文件型 Glob 的约定不足，消耗调查轮数。第二轮增加真实路径清单后该猜名问题未重现，不能继续当作当前两版失败的唯一原因。

## 关系证据没有形成完整链

本题接口返回流可由源码逐段核对：

```text
ChannelController.drawdownDetail
  → ChannelService.drawdownDetail
  → MiddleClient.drawdownDetail（HTTP 路径）
  → DrawdownController.detail
  → DrawdownService.detail
  → 中台对象原样嵌入渠道响应 detail
```

两份有效运行都未 Read MiddleClient，也未 Read ChannelController。混合版虽读到中台 Controller，仍没有读取客户端 HTTP 调用来核对连接。文件版直接从业务状态词跳到中台 Service，取得了两端字段，但没有完成这条返回关系的核查。

此前 3／3 标注组是 channel-fields、middle-booking-fields、success-boundary；旧复核文件的 relationCoverage 本来就是 null。它们说明关键字段和状态依据已出现，不能证明客户端、HTTP 路由或页面消费关系都已覆盖。我们应当把关系端点与连接依据分别记录，不能把“文件都读到”当成“业务链路已确认”。

资料边界也有局部缺口：工程配置只登记了 Mifos Web 前端，它属于 fineract-platform；没有登记渠道页面工程。没有证据把它认作渠道运营页面。当前提示构造主要提供授权路径与资料状态，未直接提供配置中已有的系统／应用／仓库职责映射；业务目录定位失效后，更容易按“唯一前端仓库”猜测目标。当前模板不能替代已经缺失的历史逐字请求快照，但它显示该导航能力仍待补齐。

## 收尾丢失的是调查状态，不是本题关键源码

`runtime.py:233` 的独立 compose 只重组用户／历史最终回答和 Read／SearchCode 原文。它不传递工具调用记录、查过但未命中的对象、待核对连接、未找到的页面消费者及下一步任务。最终两份冻结输入均未遗漏原文块，关键返回字段确实还在其中；本题不能简单归因于关键源码被上下文裁掉。

保留一次无工具答题解决了第一轮持续调用工具不收尾的问题，但当前还没有按证据完成度控制结束的机制：七轮调查用完就转入答题，未完成项没有形成单独的结构状态交给答题器。答题器因此面对原文自行重新组织调查结论；它可能正确复述局部代码，同时错误扩大结论或建议效果。

应传递可核对的简短调查状态，例如已确认的接口对象、已有证据、未连接的调用端点和未确认的消费端。它用于限制结论范围，不把搜索失败当成“功能不存在”的实现证据，也不要求记录模型私有思考。

## 答案与评测本身也需要分清边界

原题同时问“运营在页面区分”和“当前渠道接口能直接支持吗”，“直接支持”至少可能指返回 JSON 足够、已有明确原因字段、页面已经呈现。这三种解释不同。只凭“不能直接区分”的标题不足以判整篇错误；之前的标题判断偏笼统，应以具体断言复核，原答案与旧复核记录保留不覆盖。

可以明确核对的问题是：

- 文件版对“细粒度状态是否透出给运营页面”作否定判断，却没有页面消费端证据；它引用的 detail 已包含 booking／payments 字段，缺少独立顶层字段不能用来论证响应数据不足。这里应认定为范围混写与页面断言缺乏依据，不把所有否定措辞都当成源码事实错误。
- 两版都没有找到实际页面消费者，仍断言增加后端枚举就能直接改善页面，混合版甚至假定未适配的前端已有 fallback。
- `TO_BOOK` 只能说明待入账；把它与入账失败不加区分也不准确。
- 文件版列出付款枚举 `PENDING`，实际 DrawdownOrder.PaymentStatus 定义为 `TO_SUBMIT/PROCESSING/SUCCESS/FAILED/RESULT_UNCONFIRMED`。它没有读取完整枚举声明，错误地补全了值。
- 在没有消费端依据时，“只能改一处，哪里收益最大”无法被可靠排序；模型应给条件建议，而非承诺最高收益。

两次后续固定证据复验进一步表明，结构化格式也会错：文件版知道字段已透传，却遗漏生产端引用而被程序降成未确认；混合版把后端响应构造标记为 ui。后置检查只核对“模型自己声明的对象和层次”，会继承错误归属；对合法语义设置过窄的引文契约又会损失完整性。已经修复的局部问题见事实分层复验，接口对象身份和连接核查仍未实现。

## 改进顺序

1. 先修真实工具缺陷：递归 Glob 语义、Grep 的大小写／整词控制及正确的目录发现方式。用这次实际调用模式复验。
2. 提供短的工程职责导航：复用已有系统／应用／仓库配置，标明渠道页面资料是否可用；导航帮助选范围，不能充当实现证据。
3. 维护简短调查状态：本题接口对象、待验证连接、支撑片段、未确认消费者。由缺口决定下一次搜索，把补读客户端等关键连接优先于无目标扩搜。
4. 按问题边界组织收尾：接口返回、展示映射、页面实现分别作答，已确认和未确认项共同传递；预算耗尽不自动等于调查完成。
5. 最后验证结论检查的收益。保留原题做已知回归；新题明确接口与页面边界，同模型同预算验证，再用新保留题和完整 Agent 检验泛化。

以上为诊断和后续修改顺序，本轮未修改运行时代码或执行新模型调用，不能把这些改进写成已经实现或已经验证有效。
