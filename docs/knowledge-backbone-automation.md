# 知识主干自动对照验证

本流程遵循[知识主干整改方向](knowledge-backbone-direction.md)。目标是持续比较同题有无主干时的答案质量与调查成本。它不会用“读了知识文件”或“工具调用减少”替代有效性判断。

## 一条命令运行

在项目根目录执行，使用本地已登录的 Claude Code 和当前模型设置：

```bash
python3 scripts/evaluate_backbone.py --suite evaluations/withdraw.json --judge --repeats 2
```

默认比较两组：原代码、README、需求；相同资料加当前主干（自动项目总览、按需业务流）。默认 4 题 × 2 组 × 2 轮，共 16 次答题；启用 `--judge` 再增加 16 次评审调用。默认并发 2，每次调用超时 240 秒，CLI 每次预算参数为 1 美元，但它不等于实际网关账单。使用实际模型服务会产生调用成本。

输出目录自动生成在 `.data/evaluations/backbone-时间戳/`。运行结束打开 `report.md`：

- 汇总配对耗时、工具调用、工具错误、评分与额外错误。
- 逐题查看有主干减无主干的差值，并保留业务流、业务规则、普通代码等题目分类。
- 每个答案、检索轨迹、模型报告的名称、用量、评分理由及源码依据均可追溯。
- `summary.json` 可供后续页面或其他脚本读取；`protocol.json` 和 `inputs/` 保存本轮题库、设置和代码／主干快照。

只跑一轮可用 `--repeats 1`，适合验证流程是否正常，不适合宣称稳定提升。省略 `--judge` 则只自动采集成本，质量标为待评。`--prepare-only` 只冻结输入，不调用答题或评分模型。不要把流程自动化误认为自动定时运行；当前是按需命令。

答题或启用的评分调用失败时，脚本保留结果和报告并退出 2；全部完成退出 0。退出 0 只表示评测完成，不表示知识主干有效。

## 换成真实复杂项目

复制 `evaluations/withdraw.json`，修改 `projectConfig`（相对题库文件）及 `cases`，再通过 `--suite` 指向新文件。项目配置中的本地仓库和业务基线路径沿用项目现有规则。脚本复制这些仓库并保留 README、原有项目指引及配置的需求资料；仅在实验组增加指定的业务基线。基线目录里的 Markdown 文件及其相对层级被保留。

每题包含 `id`、`question`、`checks` 和可选 `category`。`checks` 必须是依据源码确认过的判分标准，只交给评分者，不放入答题问题或知识主干。建议从实际历史问题选题，覆盖业务别名、跨系统职责、消息／回调衔接，并保留普通代码题。不得为了让主干胜出而删掉对照组已有的背景资料。

若源码本身已经包含同样的业务地图，对照测得的是额外接入主干的增量收益，这种情况应如实保留并记录。换题后也应更新题库的 `scope`，说明是真实问题、已知回归题还是合成场景。

当前内置题库只适用于三个提款演示仓库。不能只换仓库、继续用提款题评分；也不能把这里的分数当成复杂项目验证结果。业务实现变化时先复核标准，避免用过时标准给正确答案扣分。

## 如何解释评分

评分在新会话里完成，读取冻结的源码与需求；不主动提供待评答案的组别和原答题轨迹。各组评分者均可读取相同的所有版本业务文档以核查引用；业务约定不能替代源码事实。评分者与答题者使用同一模型服务，因此只是模型初评，并非独立人工评审。答案和临时路径仍可能透露组别，不宣称严格盲评。

逐项完整满足记 1，否则记 0，同时记录评分项之外的错误。得分项必须同时给出候选答案中实际存在的原文与源码依据（允许 Markdown 样式、空白差异和省略号分隔的原文片段），防止评分者用自己查到的内容替答案补全。格式不合法或满足项没有依据时，评分失败，不能按零分处理。分数可能有误，尤其需要复核两组出现分差或互相矛盾的地方。

人工可复制结果目录中的 `review-template.json`，逐项填 0 或 1，记录错误，然后无需再次调用模型即可重新生成报告：

```bash
python3 scripts/backbone_report.py .data/evaluations/你的结果目录 --reviews 你的人工复核.json
```

人工评分覆盖该答案的模型评分。未复核项保留 null。成本只汇总各组都成功的同题同轮区组，质量只汇总各组都有评分的区组；缺失不当作错误。原答案和原评分不会被覆盖。

结论应分别看：关键流程有没有少漏、源码结论有没有更准、调查成本有没有降低。工具次数不是无关搜索次数，当前未自动判定首次正确定位和无关检索，需要查看 `toolTrace`。首次实测发现，同一服务的评分者仍会宽松给分、忽略矛盾或改写答案引文；当前自动评分不适合无人复核地决定整改是否有效。小样本波动、评分误差和知识维护成本都不能从总分里消失。

数据库图谱目前不参与此对照；这验证的是文档主干接入效果，不是图谱结构带来的额外收益。

评分规则修正后，可以只重新评审已有答案，无需重复答题。旧评分及评审轨迹保存在每次运行目录的 `review-history/`：

```bash
python3 scripts/evaluate_backbone.py --rejudge .data/evaluations/你的结果目录 --workers 2
```

## 其他对照与检查

`--comparison current` 保留三组诊断（无主干、生产方式、全部文档注入）；`--comparison rewrite --legacy-baseline 冻结旧文档路径` 比较无主干、旧文档与新版。`--cases` 可选题，`--blocks 题目id:轮次` 可补跑完整区组，补跑结果单独存放，不自动择优替换历史结果。

评测汇总逻辑的回归检查：

```bash
python3 -m unittest discover -s tests -p 'test_backbone_evaluation.py' -v
```
