# 业务补充知识使用指南

知识主干与词云（知识图谱）的定义、作用及后续整改标准见 [项目整改指导方向](knowledge-backbone-direction.md)。

业务补充知识记录源码难以可靠推断的项目特有语义、边界、术语歧义、隐式跨系统关系和例外。源码支持当前实现，需求原文说明目标。调用链、类名、字段、URL 和可由源码直接确认的细节随代码维护。

## 新目录与资料索引

```text
knowledge/business-context/
├── README.md             资料范围、依据和更新说明
├── terminology.md        项目特有术语、别名和歧义
├── boundaries.md         系统职责边界和不负责事项
├── cross-system.md       隐式跨系统关系和事件衔接
└── exceptions.md         业务例外、适用范围和待核查项

knowledge/generated-code-map/
├── project-index.md      简短的项目资料索引（可选）
└── ...                   自动生成的目录、文件和符号导航
```

`project-index.md` 只用于列出资料位置和简短导航。运行时不再把历史 `project-overview.md` 全文自动注入每一题；业务补充知识和代码地图均由模型按问题需要读取。结构资料只帮助定位，不能替代源码证据。

注册工程登记只创建上述目录，不自动复制配置中的资料；请使用显式资料导入或人工维护步骤。旧 `knowledge/baseline/` 可以在确认内容分类后迁移，不能整目录原样继续扩写。

资料应说明适用系统、关键语义、边界、例外、依据与核对日期。区分业务约定、当前实现与未知部分；没有证据的异步步骤或外部职责不要补写。只有业务语义本身难以消歧时，才附少量稳定入口作为线索；它不能替代源码确认。

下文是通用写法示例，不代表当前提款演示已经实现其中的产品、担保后处理或核心放款能力。

## 编辑与发布

管理员在「业务补充知识维护」的「业务文档」页打开或新建 Markdown。保存时比较打开时的原文，遇到其他人已保存的修改需重新打开、合并后再保存。注册工程保存到工程数据目录，兼容工程使用配置中的 `knowledge.businessContextRoot`。仅配置旧 `baselineRoot` 的工程可查看历史原文，迁移后可编辑。

保存后的原文直接用于下一轮包含业务补充知识的问答。资料变化会更新 Pi 会话。需要更新知识图谱或实体关系展示时，在「结构化视图」执行导入。Markdown 是业务知识的维护源。

资料总览和业务关系图会显示结构化视图的导入状态。原文变化后，保存结果与上次导入内容不同时显示待更新，可继续查看已有投影。刷新投影时选择 Claude Code 或 Markdown 规则解析。

管理员接口使用 `/api/projects/<projectId>/knowledge/context/files` 列出文档，并在路径后附编码后的 Markdown 相对路径读取或保存。保存请求包含 `content` 和打开时的 `previousContent`，新建文件时后者为 `null`。原文变化返回 HTTP 409。

## AI 修订建议

管理员可对已保存的文档选择整份或一个章节，填写变更说明、相关需求或代码调查结果。建议使用默认 Pi 模型，输入限于所选原文和补充材料。建议列出修改说明、建议正文、依据及待确认事项。生成建议后可在原文编辑器继续调整，或审阅后点击「确认并保存」。

业务依据可注明来源及确认状态。需求表示目标，源码调查用于发现当前实现差异。只有授权业务方确认后，才能把推测写成业务约定。「待业务确认」的建议保留核对事项，管理员仍可回到原文独立修订。

`POST /api/projects/<projectId>/knowledge/context/suggest` 接受 `name`、`previousContent`、`note` 和可选的章节起始行 `sectionStart`。带修改的建议返回完整待保存稿 `proposalContent`，发布使用同一 Markdown 保存接口。

## 推荐内容

### 业务术语

```markdown
## 极优

极优是再担保类型产品，代码中一般用 JY 表示。
```

### 系统边界

```markdown
## 贷款中台系统

贷款中台负责提款、授信和还款的业务编排，不负责核心账务处理。
```

### 业务能力

```markdown
## 提款结果处理能力

贷款中台获取提款最终结果，并根据产品类型执行提款后处理。
```

### 跨系统语义或例外

```markdown
## 担保产品边界

担保类产品的提款成功通知由贷款中台触发，担保处理系统负责生成担保文件；具体调用关系和当前实现必须从源码确认。
```

### 可选语义入口

只有业务名称无法定位、且入口具有稳定语义时才补入口。入口是导航提示，不是实现说明；不要把类名、方法名、路径或行号写成业务事实。

```markdown
## 提款申请语义

用户在渠道发起提款，中台负责申请编排；入口名称仅作为待核查的搜索线索。

### 调查入口

- 渠道侧提款申请 | PAGE | （按需补充稳定页面名）
- 中台提款编排 | CONTROLLER | （按需补充稳定入口名）
```

如果入口不是业务语义所必需，可以不填写；自动代码地图和源码搜索负责普通文件、类和方法定位。

### 业务关系

```markdown
## 担保产品提款后处理

担保类产品提款成功后，会触发担保处理并产生担保文件。
```

### 独立规则

```markdown
## 担保产品提款规则

产品属于需要担保的产品时，提款成功后必须进入担保处理。
```

## 不需要填写

- JSON 或 YAML；
- 完整包名和文件路径（入口只写短名称）；
- 方法调用链；
- SQL 和数据库字段；
- 可以直接从代码索引得到的技术细节；
- 不确定的推测。

## 提升调查效果

如果业务名称和代码命名差异很大，可以在自然语言中补充真实业务别名；只有确实存在语义歧义时，再补一条入口线索：

```text
极优在代码中一般用 JY 表示。
提款结果处理相关业务通常称为 WithdrawResult。
```

不要把完整方法调用链当作需要手工维护的主干。当前 Agent 根据业务语义和代码地图按需搜索源码，入口失效时调整检索，并如实说明尚未确认部分；Python 不执行入口解析或固定次数的索引搜索。

## 内容规模

业务补充知识应短小、可核查，不要求一功能一文件。优先补充：

1. 项目特有名词；
2. 关键跨系统关系；
3. 容易从代码误解的业务规则；
4. 代码命名与业务叫法之间的别名；
5. 只有业务语义无法消歧时才补少量稳定入口线索。

重复的技术过程、完整调用链和临时问题结论不要写入业务补充知识。
