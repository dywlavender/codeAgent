# 知识主干链路提示词重新分析

日期：2026-09-10。范围：问答的资料挂载、常驻指令、每轮追加提示，以及相邻的知识结构化和评审提示。

依据：当前源码、当前示例工作区，以及临时目录中的提示拼装与校验函数复现。没有调用真实模型；文中的行为影响属于待验证判断，不能当作改写后的收益证明。本次只新增分析文档。

## 1. 判断

需要优化。当前已经遵循“业务补充知识按需读取、源码确认当前实现”的方向，保留这些约束即可。优先解决三件事：本轮范围只有一个权威来源；跨仓库扩展跟随实际线索；明确业务知识何时值得读取、可以支持哪类结论。

前两项有直接的文本矛盾或误导性表达。第三项是质量优化建议：当前提示没有禁止正确使用业务知识，但更多篇幅用于约束不能做什么，对如何利用业务语义的说明不足。

另一个前提需要分开看：提示词不能制造资料本身没有的语义增量。当前根工程仍配置 `knowledge/baseline`，其中有阶段表、接口检索词和类名入口；提示词称其为业务补充知识，不意味着资料已经完成了最新方向要求的分类迁移。此结论只适用于本次核查的根工程，不推断其他注册工程。

依据：[最新方向](../../spec/knowledge-backbone-direction.md)、[当前配置](../project.config.json)、[当前提款资料](../knowledge/baseline/withdraw-flow.md)。

## 2. 实际生效链路

```text
QueryService.ask
  → 根据模式挂载资料、生成 CLAUDE.md
  → 校验本轮系统／仓库范围
  → ClaudeCodeRuntime.build_command
      → 追加本轮目录清单、工具用法、可选短索引
      → 原始用户问题作为 -p 参数

```

问答不会调用知识实体、关系或入口的数据库检索。知识结构化服务读取 Markdown、提取实体和关系，是管理链路；改它的提示词不会直接改变问答每轮读到的原文。

## 3. 优先修改的问答提示

### 3.1 统一本轮范围，去掉重复目录清单

**事实。** `_claude_instructions()` 调用不带仓库范围的 `workspace_sources(root)`，把全部仓库写为可用来源，又内嵌一次 `search_instructions()`。Runtime 使用带范围的清单再次生成同一段说明；`project_index()` 还会重列目录。

当前示例限定 `channel-service-repo` 时，常驻指令仍包含 `loan-middle-repo`，追加提示则不包含，并声明未列出的代码目录没有授权。两段都使用“本轮”表述。

**影响判断。** 模型可能选错搜索根目录，产生无效调用或错误的覆盖范围说明。本次没有验证范围外文件是否能被 CLI 实际读取，不能把文本冲突扩大描述成已经证实的权限突破。

**建议。** `CLAUDE.md` 只保留通用调查规则；项目、模式、版本、本轮来源和短索引放在每轮追加层。来源目录只列一次，索引只提供资料导航。不要把每个请求的 scope 写入共用的模式文件。

位置：`workspace.py:432`、`:467`、`:468`，`claude_runtime.py:71`，`service.py:138`、`:141`。

### 3.2 跨仓库调查不应暗示“前一个仓库没找到才能继续”

**事实。** 当前原文为：

> 跨仓库调查请分别搜索相关仓库；一个仓库没有匹配结果时，再搜索其他相关仓库。

后半句容易把“没有匹配”读成扩展仓库的前提。实际多应用调查通常已经在渠道找到入口，随后需要根据调用线索到中台继续查。

**建议替换。**

> 跨仓库搜索分别指定相关仓库目录。根据已读源码中的调用、事件或路由线索，以及相关业务资料中的系统边界，决定是否继续调查其他已列出的仓库。没有匹配时调整检索词或范围；发现匹配后也可能需要跨仓库继续核查。

这仍由模型判断相关性，不要求固定顺序或固定读取数量。是否减少遗漏，需要后续真实题目对照。

位置：`workspace.py:70`。

### 3.3 补齐业务知识的正向用法和证据边界

**事实。** 现有原则已写明资料按需读取、业务知识不是实现替代品、冲突分别说明。没有明确说明：什么情况值得优先查看业务知识；仅涉及术语或业务约定时，知识文档本身可以支持什么结论。重要结论的引用要求也只明确覆盖代码。

**影响判断。** 可能出现两个方向的偏差：遇到业务别名仍长时间在源码中盲搜；回答业务约定时把所有结论都转为实现调查。不能据此断言现有模型必然如此。

**建议新增或合并。**

> 问题涉及项目特有术语、名称歧义、系统职责、隐式跨系统关系或业务例外时，优先查看相关补充知识；已有明确代码位置且只问局部实现时，可以直接读取源码。
>
> 业务补充知识可以支持有来源的术语解释和业务约定，引用时说明适用范围；它不能证明代码已实现该约定。需求原文支持提出过的目标，源码支持当前实现。代码地图和项目索引只提供定位线索。
>
> 资料中的待核查内容保持为待核查；资料与实现不一致时分别说明。重要业务约定引用文档位置，重要实现结论引用源码位置。

不要增加“每题必须读主干”、固定问题分类器或完整业务流程注入。这里的触发条件是帮助模型判断相关性，不是强制检索工作流。

位置：`workspace.py:473` 至 `:482`。

### 3.4 把停止条件和回答要求说得更具体

**事实。** 当前只写“不要为了完整调用链而无止境向下搜索，只调查回答当前问题必要的内容”。方向正确，但缺少如何判断已经足够的正向标准。

**建议合并进现有原则。**

> 已有证据足以回答用户关心的行为、关键条件和结果，且没有会改变结论的未核查线索时，可以结束调查。相关线索因资料范围无法继续确认时，说明具体缺口。直接回答用户问题，随后给出关键依据和必要边界；无需输出固定调查模板。

对于调用链问题，只沿与答案相关的真实调用或异步线索展开；不列全项目分支和异常清单。保留现有“总结不能比正文证据更强”。

## 4. 次优先级问题

### 4.1 主动不提供的资料，被写成配置错误

`workspace.py:435` 至 `:439` 只按目录是否挂载生成“未配置有效目录或目录不存在”。在新布局的 `none` 模式，业务知识和代码地图本来就是主动不提供，仍会收到这条说明。

建议区分“本模式不提供”“目录缺失”“目录为空”。其中前两类的混淆已复现；空目录状态应复用已有资料状态能力，不靠模型猜测。动态模式说明与可用性从同一来源生成，避免 `service.py` 和 `workspace.py` 各维护一套。

### 4.2 索引兼容与组合方式需要明确

`project_index()` 只识别“业务补充知识”“自动代码地图”，不识别兼容的“业务基线”。同时采用找到第一个索引就 `break` 的策略；组合模式下，两类资料都有索引时，只注入业务索引，代码地图仍然可读，但它的索引正文没有注入。

建议明确一个权威项目索引，或者分别提供两类简短导航。对旧目录显式支持 `project-index.md` 或明确迁移规则。不要因为兼容旧目录，就恢复自动注入 `project-overview.md`。

位置：`workspace.py:89` 至 `:110`。

### 4.3 结构化提示应与实际提取约束一致

当前 `_BASELINE_PROMPT` 仍以“人工业务基线”开头，并强调流程、步骤和调查入口。建议改为“结构化已提供的业务补充知识”，优先保留术语、职责边界、例外和原文明确的关系；已有流程可以忠实提取，不要求补齐全流程或入口。

有一个确定的接口不一致：提示词说关系谓词“例如”五种英文类型，代码只接受 `RELATION_PATTERNS` 中的五种。使用当前资料中“提款申请流程包含信息准备……”的原句，传入 `CONTAINS` 后关系被丢弃。应明确仅支持这五类，无法忠实表示的关系暂不输出；是否扩展类型另行决定，不能要求模型硬套近义关系。

此外，默认抽取工作区为空，共用 Runtime 仍追加“当前没有可用的业务资料或代码目录”，而待提取原文其实已在问题的 `text` 中。没有证明这一定造成抽取失败，但属于不相关的问答指令。建议抽取任务使用独立提示配置，说明 `path` 仅为来源标识，直接处理已提供的 `text`，无需搜索文件。

位置：`baseline_service.py:395`、`:402`、`:441`、`:600`。这部分优化服务于知识管理，不能计为问答收益。

### 4.4 评审需要适应真正的业务语义题

保留候选答案原文引文、实现回源码核查、评分标准冲突单独处理这些规则。建议调整三处：

- 把全工程共用的“真实签约先完成”案例改为通用的“局部校验不能证明完整业务状态，结论不能与自身证据矛盾”。具体案例保留在相应题目的评分要点中。
- 按评分项性质确定证据：实现项读源码，术语／约定项核对该项指定的适用业务资料。当前 `evidence` 示例只有源码位置，应允许业务文档位置，并说明资料版本。
- 将“不确定均 false”限定为“未满足该项所要求的结论”。若评分项本身要求识别当前资料无法确认的边界，准确说明边界应可得分；不能奖励猜测确定结论。

这些是面向业务语义评测的改进建议，本次没有重新审查历史答案，也不认定历史评分因此全部无效。原参考答案只进入评审的边界继续保留。

位置：`evaluation/harness.py:102` 至 `:114`；`evaluation/scoring.py:44` 至 `:49`。

## 5. 可直接评审的通用调查原则草稿

以下替换当前调查原则，具体项目、模式、目录与资料状态由每轮追加提示给出：

```text
你回答当前工程的业务与代码问题。根据用户问题决定调查范围，直接回答问题，并为关键结论提供依据。

资料使用：
- 源码用于确认当前实现；README 提供项目背景，具体行为以源码核实。
- 需求原文表达提出过的目标和约束，不代表已经实现。
- 业务补充知识用于解释有来源的项目术语、业务约定、职责边界、隐式跨系统关系和例外。引用时说明适用范围，待核查内容不能当作已确认事实。
- 项目索引、代码地图和入口名称只帮助定位，不证明业务行为。

调查与作答：
1. 问题涉及业务语义、名称歧义、系统边界或例外时，优先查看相关补充知识；明确的局部代码问题可以直接读源码。无需每题读取所有资料。
2. 当前实现结论必须读取相关源码。根据实际调用、事件、路由和相关业务线索决定是否继续调查其他已列出的仓库；找到第一个入口并不代表问题已回答。
3. 调查用户关心的行为、关键条件和结果。已有证据足以回答，且没有会改变结论的未核查线索时，可以结束；无法确认的相关环节应说明具体缺口。
4. 区分资料约定、代码已实现和仍待确认的部分。资料冲突时分别说明，不根据名称或文档链接猜测实现。
5. 重要实现结论给出源码路径与行号，重要业务约定给出文档位置。金额单位、枚举和前置条件要有依据，局部字段检查不能扩展为完整业务状态验证，总结不得强于证据。
6. 只报告影响答案的资料缺口；未找到、访问失败、源码已确认要区分。

当前会话只允许读取和搜索文件。
```

每轮追加提示保留：本轮唯一来源目录清单、模式与可用性、AST 版本（适用时）、必要短索引、工具参数要求、范围外情况处理。`Glob/Grep` 明确 path、`Read` 不接受目录、正确路径仍被拒绝时报告来源问题等已有规则有实际用途，可压缩去重后保留。

## 6. 对同日旧评审的纠正

保留旧评审原文件，不覆盖。以下以本次源码和现场复现为准：

| 旧评审说法 | 本次核对 |
| --- | --- |
| 当前有主干模式注入 `.data/knowledge/generated-code-map/project-index.md` | 当前模式来源只有旧业务基线和三个源码仓库，没有代码地图来源，也没有索引正文注入。文件存在不等于进入该模式。 |
| `CLAUDE.md` 跨轮不更新 | `service.ask()` 每轮调用 `ensure()`，后者重写文件。实际问题是生成内容未使用本轮 scope。 |
| 无提示词版本号，无法判断历史提示词 | 评测已保存 `CLAUDE.md` 和包含追加提示原文的 `command.json`，可以对比历史文本。显式版本号便于统计，优先级低于范围和语义问题。 |
| 每轮重写是无意义写盘 | 来源或模式元数据变化时重新生成有意义。应先划分稳定与动态内容，再决定是否减少写盘。 |

当前现场：`CLAUDE.md` 为 1680 字符；未限定范围的追加提示为 1043 字符；常驻文本中确实完整重复了同一段检索说明。这是结构冗余，不能仅据文本体积推断显著性能收益。

## 7. 本地验证与后续验证

本次通过直接调用当前函数复现，未改产品代码：

| 检查 | 结果 |
| --- | --- |
| 限定渠道仓库后，常驻清单是否仍列中台仓库 | 是；追加清单不列，冲突确认 |
| 常驻指令是否包含一整段重复检索规则 | 是 |
| 当前有主干模式是否自动注入代码地图索引正文 | 否 |
| 新布局无主干模式是否把主动不提供写成缺少配置／目录 | 是 |
| 组合模式有两个索引时是否同时注入 | 否，只注入业务索引 |
| 旧标签下的 `project-index.md` 是否注入 | 否 |
| 默认空抽取工作区是否追加没有业务资料的说明 | 是 |
| 原文有包含关系，输出 `CONTAINS` 是否被接受 | 否 |

落地后先保持资料、问题、模型和评分标准一致，只比较旧／新问答提示，覆盖局部代码、业务术语、跨系统现象和资料与实现不一致的正常题型。核查结论正确性、业务遗漏、无关搜索和引用，再看耗时、调用量与上下文消耗。历史题目若没有语义增量，不能据其结果否定或证明业务知识的语义价值。

评审提示的改写单独核对；不能同时换资料、答题提示和评分标准后，把所有变化归因于提示词。真实业务补充知识的增益，仍按最新方向中的资料分组协议验证，保留正常资料和旧批次。
