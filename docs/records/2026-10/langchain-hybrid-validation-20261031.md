# LangChain 迁移与混合检索实测

日期：2026-10-31。

## 结论

主问答已经迁移为项目自有 LangChain 1.2.18 Agent，直接使用 `.env` 中的兼容模型连接，管理会话上下文、只读文件工具、调查预算和最终答题。混合检索链路已经实现并接入可选 SearchCode 工具，但本次未证明稳定的问答收益，精排也未达到所要求的 50–200ms 目标。默认保留文件工具，混合检索需显式启用。

真实 Qwen 单题对照中，两版最终都取得了该题全部 3 个已标注证据组，却仍把“只看 displayStatus 无法区分”概括成“渠道接口不能支持”。完整渠道响应已经返回 detail，其中含 payments 和 booking 的状态。这个反例表明，本题错误不能只解释成资料缺失或检索未命中；需要核对结论是否与已经引用的源码一致。该判断是助手源码核对，尚未经过用户人工复核，不给出虚构的正确率评分。

## 实现范围

- `query/langchain_agent/`：使用 LangChain `create_agent` 和兼容 Chat 模型，提供 Read／Glob／Grep；按本轮工程、仓库范围和资料模式限制来源。每轮提供真实授权目录，避免猜测仓库名称。
- 会话保存最近六个完整用户回合；超过字符预算的旧工具正文标为已废弃，源码更新后历史 Read 原文作废，历史 SearchCode 原文在追问时重新取得。工具调用和结果保持配对。
- 总模型调用次数包含最后一次独立无工具答题。到达保留额度时，程序将已取得的原文交给无工具模型调用，不携带工具定义或工具调用历史。取消和总时长限制同样覆盖答题阶段；事件保存完整工具原文供核对。
- `codeintel/hybrid/`：Java、Python、JavaScript、TypeScript 按函数和类声明组织；大类的声明、字段与方法分别组织，其他未支持格式保留标明类型的文件区域，Markdown 按章节。没有将 token 窗口冒称为函数。
- BM25 与向量并发召回，各取至多 80 项，以排名融合合并到 Top-50，权重 0.6／0.4。使用本地 ONNX 多语编码器和 Cross-Encoder，模型不通过推理服务上传源码。
- SearchCode 上下文最多 12,000 字符、300 行、单元最多 100 行，计入定位头和续读标记。带源码废弃标记、截断提示及可直接交给 Read 的位置。已过期索引条目仅返回定位提示，不把旧正文作为当前实现依据。
- 索引只能显式准备或更新，按保存的文件修改时间／大小观察复用未变化原文，以 Git diff 对比已索引原文与变化原文，仅重新解析变化文件、嵌入新增或变化单元。删除从索引移除；未变化片段复用向量。无变化更新不重写向量或创建新索引版本。结构格式升级与源码变化分别记录。

本轮没有生成 AST 管理页的资料；工程 AST 目录仍为 0 个文件。结构解析发生在用户要求的显式检索索引准备中，服务启动、页面加载和问答不隐式运行解析器或下载模型。程序尚未实现业务“必要补查任务”或语义结论一致性的通用规则控制器。

## 本地索引与模型

工程语料 8,096 个文件，与 `retrieval-20261030-requirements-restored` 冻结原文逐字一致。包括 5,617 个 Java 文件、1,190 个 TypeScript 文件及正常项目资料；没有删减需求或给检索器提供参考答案。

首轮结构索引 54,739 个单元，嵌入耗时约 1,432.99 秒，不含模型下载。增加 TS／JS 结构支持后显式升级为 61,982 个单元，新增嵌入 8,411 个，复用 53,571 个，耗时约 171.39 秒；原文没有变化。最近一次无变化更新约 4.39 秒，0 个新嵌入，复用全部 61,982 个单元。单次耗时不能视为跨环境性能保证。

- 编码器：`Xenova/paraphrase-multilingual-MiniLM-L12-v2`，量化 ONNX，384 维。
- 精排器：`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`，原作者发布的 ARM int8 ONNX。
- 环境：本机 macOS ARM64、Python 3.14、ONNX Runtime CPU，4 个推理线程；模型输入最多 256 token。该输入上限是模型表示限制，不改变保存的函数原文单元。

## 检索对照：覆盖有局部改善，精排目标未通过

仅比较 12 道已知开发题，最终上下文均为 12,000 字符。标注来自助手源码核对，仍待人工复核；覆盖不等于材料充分或答案正确。新旧候选数、原文规模、行数与定位开销不同，因此下面是整套配置的对照，不能归因到单个组件。

| 配置 | 候选标注覆盖 | 最终上下文标注覆盖 | 改善／退化 |
| --- | ---: | ---: | --- |
| 原窗口 BM25，Top-40 | 72.2% | 34.7% | 对照 |
| 结构＋混合 Top-50＋200ms 精排预算＋行数约束 | 57.6% | 39.6% | 3 题改善、2 题退化 |

此配置也未超过前一轮方法单元、原文预算配平与整段保留对照的 45.1% 上下文覆盖，不能宣称新组合已经优于之前方案。

200ms 下精排 0／12 次完成，全部保留混合排序。尝试精排的耗时中位数约 206.54ms，最慢一次约 583ms；定时终止推理不能保证分词等准备阶段严格按时返回，当前实现不是已经达标的延迟硬保证。50 个短片段曾测得约 95ms，不能用它替代真实代码测量。

另外对重复回调、渠道处理中、还款额度三题将精排预算放宽至 2 秒，只用于诊断精排本身，不修改产品 200ms 设置。三次完整精排约 1,066.94–1,160.72ms；重复回调上下文覆盖从混合排序的 25% 降至 0%，另外两题持平。因此当前模型既没有满足目标时延，也没有在这三个案例显示证据选择改善。不能把回退结果计为 Cross-Encoder 收益。

原始记录：[200ms 对照](hybrid-retrieval-20261031.json)、[三题放宽预算诊断](hybrid-rerank-relaxed-20261031.json)。

## 真实模型：程序能够收尾，核心结论仍需修正

模型请求与接口报告名称均为 `qwen3.8-27b`。两版使用同一演示问题、正常资料和相同预算：非思考模式、temperature=0、每次最多 2048 输出 token、工具上下文最多 64,000 字符、总调查最多 300 秒、最多 8 次模型调用且不重试。它不是生产默认 12 次调用／4096 输出 token 的全部能力验收，也不代表该模型其他配置的能力。

首轮真实运行暴露两个迁移问题：遗漏授权目录清单造成猜错仓库；仅在最后一轮移除工具列表仍未可靠转入答题。两版均用完 8 次调用而没有最终正文，文件版约 28.49 秒、混合版约 40.45 秒。原记录保留：[文件版](langchain-files-channel-20261031.json)、[混合版](langchain-hybrid-channel-20261031.json)。其中协议 completed 不表示答题成功，应检查 stopReason=budget 和实际正文。

修复目录提示及独立收尾后，用户重新批准第二轮两次对照。最多 7 次调查＋1 次独立无工具答题，两次均产出模型正文：

| 第二轮 | 模型调用 | 耗时 | 累计输入 token | 本题已标注证据组 |
| --- | ---: | ---: | ---: | ---: |
| 文件工具 | 8 | 61.39 秒 | 44,152 | 3／3 已 Read |
| 混合检索 | 8 | 66.28 秒 | 92,866 | 3／3 已 Read |

输入量是累计 API 用量，不是美元账单；缓存计费等未核实。仅一题、每组一次，不能据此宣称普遍性能差异。

源码核对的关键反例：渠道 `ChannelService.drawdownDetail` 第 125–136 行返回 `middleStatus` 及完整 `detail`；中台 `DrawdownService.detail` 第 257–265 行返回 `payments[].status` 与 `booking.status`。因此应区分：

- 只看 `displayStatus`：它把多种非终态合并为 PROCESSING，不能细分原因。
- 读取完整渠道详情响应：已有 `detail.payments[].status` 和 `detail.booking.status` 可供区分。
- 页面是否实际使用这些字段：还需核对消费端，不能仅凭后端返回值断言页面已经支持。

两版答案开头都写“渠道接口不能直接区分”，正文又承认完整 detail 中已有这些字段，混淆了接口数据能力与单一展示字段。混合版的部分状态枚举和来源说明更完整，但没有消除这个核心表述问题；关于前端自动适配、新展示枚举兼容性的断言也没有充分核实。推荐改动应先考虑消费已有字段，或在保持现有展示契约时增加原因字段，不能把改变枚举值直接认作无影响。

这不足以证明所有必要资料均已穷尽，但足以反驳“这些字段没有透出”的结论。下一步更值得验证的是接口返回事实提取、展示与数据能力分层、结论和引用的一致性，而不是继续默认堆检索组件必然有效。思考模式与其他模型的同证据对照尚未执行。

原始记录：[第二轮文件版](langchain-v2-files-channel-20261031.json)、[第二轮混合版](langchain-v2-hybrid-channel-20261031.json)、[助手源码核对](langchain-answer-source-review-20261031.json)。两轮分别获批最多 16 次问答调用，两轮各实际执行 16 次。此前另有一次仅发送“只回复 OK”、最多 16 输出 token 的连通探针，未用它作答题验收；没有追加未批准的真实调用。

## 检查与使用

相关后端 96 项测试通过，包含真实 LangChain 对本机模拟兼容接口的工具循环、独立无工具收尾、上下文配对、源码变化后旧正文废弃、调用预算、进行中的请求取消、工程隔离，以及结构分块、融合、精排回退和增量复用。前端 11 项测试及构建通过，构建保留既有体积提示；本轮没有把构建或模拟模型测试当成真实页面交互验收。

主问答默认 `BUSINESS_CODE_AGENT_RUNTIME=langchain`。重启服务加载新代码和配置。准备当前工程索引后，设置 `BUSINESS_CODE_AGENT_RETRIEVAL=hybrid` 可显式启用 SearchCode；默认 files。准备与测量命令见现行检索诊断文档及三个 `scripts/evaluation/` 脚本。

实现参考：[LangChain Agent](https://docs.langchain.com/oss/python/langchain/agents)、[短期上下文](https://docs.langchain.com/oss/python/langchain/short-term-memory)、[Retrieve & Re-rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。实际 API 已以本机安装的 1.2.18 和测试为准，未把最新版网页示例直接当作已安装版本保证。
