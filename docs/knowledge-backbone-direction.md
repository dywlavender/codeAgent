# 知识主干与知识图谱：项目整改指导方向

确认日期：2026-09-05。本文记录用户与助手对齐的产品方向，作为后续项目整改的依据。本文描述目标与判断标准，不代表这些能力已经实现，也不代表收益已经验证。

## 1. 知识主干的定义

知识主干是供大模型理解项目并持续指导代码调查的项目认知地图。它组织项目整体认识、业务术语、系统职责、完整的业务流程、关键业务关系和稳定的入口类等知识，让模型从更有依据的检索假设出发，在读取代码、获得线索、继续检索的过程中少走弯路。

它的作用贯穿调查全过程，不能收窄成“业务问题到代码入口的映射”。模型既需要知道从哪里开始，也需要知道当前调查处于业务流的哪一段、还缺少哪些关键环节，以及何时应该转向另一个系统或异步入口。

这里的“完整业务流”指在所描述业务范围内，覆盖主要阶段、参与系统、关键分支、异步衔接和必要的异常／补偿路径。完整性体现在业务层，不要求复制全部方法调用、字段和实现分支；尚未覆盖的部分应明确标出，不能把局部流程当成全貌。

## 2. 知识主干的内容与作用

| 内容 | 帮助模型解决的问题 |
| --- | --- |
| 项目整体结构、系统和应用职责 | 这是什么项目，业务由哪些系统协作完成，应在哪些仓库调查 |
| 业务术语、别名、历史名称、代码代号 | 用户的业务说法在代码中如何表达，第一次和后续检索应该用哪些词 |
| 业务全流程及关键分支、异步衔接 | 当前证据对应哪个阶段，前后还有什么，是否遗漏关键环节 |
| 业务能力、规则及有来源的业务背景 | 某段实现承担什么业务职责，为什么需要调查相关分支 |
| 稳定的页面、入口类、任务或消费者 | 从哪里进入源码，什么时候需要切换调查入口 |
| 业务对象、流程、系统、事件之间的明确关系 | 根据已获得的线索，下一步应扩展到哪些相关业务和实现 |

预期减少三类弯路：业务词与代码词不匹配；在错误系统中持续搜索；找到局部实现就过早认为业务调查已经完成。

## 3. 词云（知识图谱）的定义与作用

用户讨论中的“词云”按具有业务语义关系的知识图谱理解，不能实现为只展示词频、字号和关键词的普通词云。

知识图谱是知识主干中概念及其关系的组织与呈现方式。节点可以包括术语、系统、应用、业务能力、流程、规则、事件和入口；关系必须具有明确含义，例如：业务名称对应代码代号、系统负责某个阶段、事件触发后续流程、流程具有某个调查入口。

图谱用于帮助人和模型理解、检索和沿关系扩展项目知识。对模型而言，关键是能够取得并理解相关节点及关系；对用户而言，关键是能看懂业务上下文和调查方向。图形展示只是其中一种形式，画出更多节点和连线不等于问答能力已经提高。

知识图谱与业务文档应表达一致的业务知识。图谱是主干的组织与使用方式之一，不应成为与原文各自维护、互相矛盾的另一套事实。

## 4. 与大模型代码调查的关系

目标过程如下，表示信息如何帮助调查，不要求每道题强制执行固定步骤：

用户问题 → 借助项目认知和相关业务流形成检索假设 → 搜索入口并读取源码 → 根据源码线索与业务关系继续调查 → 确认当前实现、覆盖范围与尚未确认的部分。

主干提供背景、方向和业务覆盖参照，源码确认当前实现。模型应能用源码修正或推翻主干中的假设；业务约定与当前实现不一致时，应分别说明。

模型也可能通过 README、目录结构等资料自行建立项目认识。因此，主干的增益应相对于“已有项目资料和代码均可正常使用”的调查过程衡量，不能把对照组已有的背景信息刻意删去。

## 5. 后续整改原则

1. 优先让知识主干实际参与模型的项目理解和持续调查，不能停留在管理员维护和独立图谱浏览。
2. 同时保留整体认知与按需展开的能力，避免只给零散入口，也避免每题无差别塞入全部知识。
3. 内容优先补充项目特有术语、系统边界、跨系统业务流、异步关系和稳定入口。可以从源码直接确认的实现细节不应大量重复维护。
4. 保留必要的来源、适用范围和更新信息，使错误或过时知识可以定位和修正；维护负担要与实际收益一起评估。
5. 不要求每题必须读主干，也不强制沿既定流程调查到底。模型根据问题相关性和源码线索决定调查范围。
6. 页面应帮助用户理解业务关系以及这些知识如何关联当前调查。区分“资料可用”“实际读取过”和“对调查有帮助”，不能把读取次数当成贡献证明。
7. 本文不预设图数据库、检索算法、工具接口或固定 Agent 工作流。技术方案围绕上述作用选择；不能因为已有结构化模型，就默认其成本必然值得。

## 6. 判断是否有效

核心验证问题：同一道真实业务问题，提供主干后，模型能否更早找到正确业务范围，减少无关探索，并更少遗漏关键流程。

重点观察正确系统与入口的定位、业务术语消歧、关键业务环节覆盖、源码结论正确性及无关搜索；耗时、工具调用和上下文消耗作为辅助指标，同时考虑知识维护成本。

有主干时，模型可能因发现原先遗漏的异步步骤而读取更多文件。这可能是调查质量提升，不能仅因调用次数增加就判断失败；同样，少查几个文件也不能直接证明成功。

以真实且存在术语差异、跨系统或异步关系的问题验证，并保留普通代码题作为对照。需要区分“业务文档带来的收益”与“结构化关系在文档基础上的额外收益”。现有小示例的结果不能直接外推到真实老项目。

## 8. 复杂项目的验证假设

用户提出：复杂项目可能比当前简单示例更能体现知识主干的作用。这是合理但尚未验证的假设。应按业务词与代码词差异、跨系统职责、关键异步衔接与流程分支等实际调查困难分层验证，不仅按代码行数或仓库数量判断。

复杂项目也会增加知识过时、关系冲突和上下文负担。因此保持“简短项目总览＋按需业务流程”的组织方式，验证模型是否减少无关探索和关键遗漏。普通代码题继续保留，不能以复杂项目可能有效为由忽略当前无增益的结果。

持续回归入口见[知识主干自动对照验证](knowledge-backbone-automation.md)。自动报告须同时展示质量与成本，模型评分标为初评，不以成功运行或知识读取次数判定有效。

[自动流程首次实测](knowledge-backbone-auto-validation-20260905.md)：8次答题复核后两组均19/20，未证明稳定增益；模型评分有漏判与引文问题，不能无人复核地作为验收结论。

## 9. 诊断对照与评分标准（2026-09-08）

用户确认先修正评测，再判断主干收益。保留正常源码资料，区分代码细节题与业务现象调查题；增加无主干、仅总览、完整主干对照，单独统计流程文档相对总览的额外收益。评分标准与源码冲突时暂停该答案评分并修订，不能处罚符合源码的回答。旧答案仅在题干不变时复用，修订重评独立保存。首次正确定位、无关搜索和遗漏需有轨迹证据，不自动用工具次数替代。实现与使用见[诊断验证说明](knowledge-backbone-diagnosis-20260908.md)。

## 10. AST 对照（2026-09-08）

用户要求继续真实验证并实现AST对照。增加独立AST、相同业务总览＋AST两种处理，区分代码结构导航和人工业务流程主干的贡献；保留正常资料，按实际命令和工具轨迹区分注入、读取与收益。AST不等同业务知识图谱。生成成本与答题成本分列，旧无结构导航批次与新版分开解释。见[AST对照方案](ast-comparison-20260908.md)。

本轮产品流程进一步约定：AST 是独立的结构资料版本，由用户在 AST 管理页手动生成、查看和重新生成。项目启动、进入页面、选择 AST 问答模式和启动实验都不得隐式触发生成；源码变化只将版本标记为待更新。主对话和三组实验必须引用同一套已生成 AST 资料，实验记录保存实际版本，AST 生成耗时与答题耗时分开统计。AST 模式不提供人工业务主干，参考答案和评分要点只进入评审环节，不进入三组答题上下文。
