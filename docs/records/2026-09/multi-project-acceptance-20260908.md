# 多工程改造验收

日期：2026-09-08。结论：暂不通过整体验收。工程独立目录、数据库及基本会话隔离已经生效，但接入入口、同步归属和登记行为仍有问题。本轮未修改产品实现。

## 已通过的验证

- 后端现有 107 项测试全部通过，耗时约 22.5 秒。
- 前端现有 9 项测试全部通过，生产构建通过；仍有非阻塞的产物体积提示。
- `git diff --check` 通过。
- 临时工程 alpha、beta 位于同一配置目录，使用相同仓库 ID `core`，注册后数据库、AST 和评测目录独立。
- alpha 创建会话后，beta 历史为空；向 beta 提交 alpha 会话 ID 返回 400。
- 两个工程导入相同案例 ID `same-case`，查询各自题库获得各自问题，未覆盖。
- 在 alpha 的 AST 目录放置明确的版本测试资料，向 beta 请求该版本返回 404。此项只验证版本路由隔离，没有生成 AST。
- 浏览器打开注册表模式页面，可以从 alpha 切换至 beta；URL 工程参数改变，alpha 会话不再出现在 beta 历史中。

所有补充验证均在临时目录和临时本机服务中运行，问答使用模拟 Runtime。没有修改已有业务数据，没有调用真实模型，也没有进行大工程容量实测。

## 1. P1：兼容启动方式的前端不可正常使用

位置：`frontend/src/lib/api.js:15-18`、`frontend/src/App.jsx:105-120`、`business_code_agent/query_agent/api.py:131-136`。

复现：

1. 使用原有单工程方式启动，不提供注册表。
2. `/api/projects` 返回当前工程，且标记 `registered: false`。
3. 页面仍将该工程 ID 写入 URL；`projectPath` 无条件把请求改写成 `/api/projects/alpha/api/workspace` 等路径。
4. 后端明确拒绝没有注册表的工程前缀路径，返回 400 和“当前服务未启用工程注册表”。

实测原 `/api/workspace` 返回 200，前端改写后的路径返回 400。浏览器确实显示错误，工作区显示 0 个仓库。现有启动器和文档仍保留单工程启动方式，因此这不是只影响手写请求的边缘问题。

修复验收：单工程与注册表模式都能打开工作区、读取历史和完成一次模拟问答；前端依据部署能力选择路由，或后端允许当前兼容工程的明确前缀请求。

## 2. P1：同步命令允许工程上下文与配置不一致

位置：`business_code_agent/cli.py:137-155`。

注册表模式只从 `ProjectContext` 获取默认数据库，仍直接使用独立传入的 `--config`。另外，显式 `--db` 也可覆盖工程数据库，未校验是否与上下文一致。

复现命令形态：

```text
sync-project --project-registry <registry> --project-id alpha --config <beta.json> --offline
```

实测命令退出码为 0，alpha 的数据库中出现 beta 源码目录，类型符号为 `Beta`。这已发生实际的索引归属错误，不能靠查询会话前缀阻止。

修复验收：注册表模式默认从同一个 `ProjectContext` 获取配置及数据库；额外参数若保留，必须校验一致。A 上下文搭配 B 配置应在写入前拒绝；正常 A 同步和知识刷新仍成功。

## 3. P2：登记工程会自动导入现有主干资料

位置：`business_code_agent/project_context.py:217-219`、`_seed_project_materials`。

登记在创建布局后直接复制配置中的业务基线和需求资料，目录为空时就执行。临时 alpha 登记完成后，托管主干目录已经包含 `alpha private knowledge`。

这与最新 AGENTS.md 的“工程登记只创建边界和数据目录，不自动同步源码、索引、导入主干或生成 AST”冲突。当前架构文档描述了自动复制行为，但不能用现状说明代替用户确认的约定。现有测试还明确断言复制结果，因此测试通过没有覆盖这个验收目标。

修复验收：普通登记只建立边界；资料导入作为独立的显式操作。已有资料迁移也应有明确的源目录和执行步骤。登记测试应断言没有复制主干、没有调用同步/索引/AST 生成。

## 4. P2：规范路径仍要求重复的 `/api`

位置：`business_code_agent/query_agent/api.py:131-136`、`frontend/src/lib/api.js:18`。

后端移除工程前缀后不归一化 API 路径，内部处理器仍要求 `/api/workspace`。实测：

| 请求 | 响应 |
| --- | --- |
| `/api/projects/alpha/workspace` | 200，但为 `text/html`，返回前端页面 |
| `/api/projects/alpha/api/workspace` | 200，正确 JSON |

前端及新增 HTTP 测试共同使用了双 `/api` 路径，所以回归没有暴露规范接口失效。调用方按照约定路径请求时会拿到页面，可能表现为 JSON 解析错误。

修复验收：规范路径正确返回 JSON；重复 `/api` 如需保留则作为兼容别名。未知的工程 API 路径应返回 API 错误，而不是前端页面。

## 5. P2：注册表模式的兼容请求仍会隐式选默认工程

位置：`business_code_agent/query_agent/api.py:139-141`。

没有 `projectId` 查询参数和 `X-Project-Id` 请求头时，仍自动使用启动时的默认工程。实测注册表模式下裸 `/api/workspace` 返回 200。

默认工程目前不是随标签页变化的全局变量，因此不能据此声称已有标签页间随机串工程。但最新约定要求兼容请求明确携带工程上下文；当前裸请求仍可能在调用方漏传参数时读写默认工程。

修复验收：注册表模式的工程业务接口缺少上下文时明确拒绝；显式路径、请求头或参数正常工作。平台工程列表和静态资源无需工程参数。

## 验证边界与后续

此次基本 A/B 隔离验证没有发现之前的目录共用和跨工程会话续用问题。需要优先修复旧启动页面和同步归属，再修正登记及接口约定。现有测试应补齐上述正常接入场景，而不是只增加目录不相等的断言。

本轮没有验证运行中任务的跨标签页切换、实际大仓库性能、真实模型质量或完整历史迁移；这些不应被“107 项测试通过”覆盖性表述所替代。AST 测试版本是明确构造的资料夹，只用于验证跨工程引用拒绝。
