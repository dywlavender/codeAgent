# 知识主干效果验证页面方案

日期：2026-09-06。状态：首版已实现（页面 `#/evaluation`、评测后台服务与全部接口；验收路径见第 9 节，复杂评测平台功能暂缓）。

设计定稿：[design/mockups/evaluation-page.html](../design/mockups/evaluation-page.html)（v5 双面板对照）。布局原则：对照 = 左右两块面板面对面对比（无主干 | 有主干，各三项大数字：检查项、耗时、工具），差异是面板下一行小字（含评分来源切换）；逐题一行一题，点开页内展开答案对照与判分；运行中双面板显示两组各自进度。视觉：中性浅灰底（仅本页）、无表格/胶囊堆、免责句仅保留来源行。

依据：[知识主干整改方向](knowledge-backbone-direction.md)、[自动验证流程](knowledge-backbone-automation.md)、[首次自动流程实测](knowledge-backbone-auto-validation-20260905.md)。

## 1. 产品目标与判断

让用户在当前项目内点击一次即可启动同题有无知识主干的对照，离开页面后仍可回来查看结果，随后在页面完成必要复核。回答三个问题：业务调查有没有更完整；结论有没有更准确；为此多花或少花了多少成本。

“一键验证”可以自动完成实验和报告，但不能等同于“一键证明有效”。已有实测显示模型评分会漏判矛盾、替答案补全遗漏，还会改写引用。页面必须把执行状态、评分状态和效果判断分开表达。

首版验证文档主干在当前生产方式下的整体作用。结构化图谱目前没有进入该查询对照，不能在页面上将结果命名为“图谱贡献率”。

## 2. 入口与页面结构

在现有侧边导航中新增「效果验证」，位于「知识图谱」与「知识维护」附近，路由 `#/evaluation`。知识维护页增加次级按钮「验证问答效果」，跳转到此页。不要把验证绑定到“导入业务基线”：当前问答读取原始 Markdown，导入结构化知识与本次验证不是同一动作。

沿用现有 React、Ant Design、页面宽度及配色。主体分为「本次验证」「历史记录」「验证题库」三个页签，默认进入最近一次任务；没有任务时显示可直接启动的配置区。

本次验证从上到下分为：

| 区域 | 用户看到什么 | 主要操作 |
| --- | --- | --- |
| 标题与配置 | 当前项目、题库、问题数量、每题轮次、知识来源 | 一键开始验证；展开设置 |
| 进度／结果摘要 | 正在进行的阶段，或质量与成本对照 | 停止；查看待复核项 |
| 逐题对照表 | 每题两组结果、差异、评分来源与状态 | 打开问题详情 |
| 详情区域 | 两边答案、逐项判分及来源、检索轨迹 | 复核判分；记录错误 |

不在首页堆叠工具日志、模型提示词和原始 JSON。它们放在详情的「调查记录」及报告导出中。

## 3. 默认配置：已配置题库后一次点击即可开始

项目跟随当前工作台，首版不新增项目切换器。题库默认选择该项目上次使用的题库；当前项目预置「提款演示回归」。每题默认 2 轮，固定两组对照，默认启用模型初评。

配置区直接显示：

- 当前比较：相同代码、README 和需求；另一组额外使用当前知识主干。
- 当前题库：4 个问题，覆盖业务流程、普通代码、业务规则、业务边界；标记「演示／已知回归题」。
- 当前主干：项目总览和流程文档清单，来自原始业务基线目录。未提供总览时明确显示“无自动总览，仅按需文档”，而非误报完全没有知识。
- 本次规模：16 次答题，预计最多 16 次初评；失败答题不会继续评分。初评消耗与答题消耗分别记录。

主按钮「开始对照验证」。按钮上方已显示调用规模，不重复弹确认框。展开设置后可选择 1 轮快速检查、2 轮默认回归或自定义轮次，选择问题子集，关闭模型初评；无论选择什么都保持两组完整配对。轮次不命名为“可信验证”，两轮并不意味着结论稳定。

启动前检查当前题库与项目绑定、源码目录和主干文档可读、题目及检查项非空、本地模型命令可用。错误直接在配置区说明，例如“当前项目尚未配置验证题库”，给出前往题库的按钮。连接或认证错误若在实际调用中出现，展示运行错误即可，不为每次启动额外调用模型做连通性测试。

允许用本地 Claude Code 当前模型设置；只显示配置来源与可读取的模型名称，实际响应名称记录在报告中。当前网关无法独立核实的上游身份不显示为已确认，也不按 CLI 标称计价展示精确账单。

## 4. 运行中的交互

点击后立即创建后台任务并返回任务编号，页面进入运行态，按钮变为「验证进行中」，提供「停止验证」。同一项目首版只运行一批评测，重复点击返回已有任务。

分别显示阶段进度，而不是一个含义不明的百分比：

- 准备资料：冻结代码、主干、题库和运行设置。
- 对照答题：已结束 6/16，其中成功 6，失败 0。
- 模型初评：已结束 4/16，其中可用 3，待复核 1。可随答题完成并行进行。
- 汇总报告：生成逐题及整体对照。

每题按“无主干／有主干”显示等待、调查中、回答完成、调用失败等状态。评分在独立列中显示待评分、初评完成、初评失败、已复核。答题完成与评分失败可以同时存在。

页面刷新、切换菜单、关闭浏览器均不终止后台任务；返回页面从服务端恢复。用户主动停止时停止安排新任务，并取消当前受本批次管理的模型调用，保留已完成答案；不能仅断开浏览器连接。服务重启打断的任务标记为中断，保留结果，不自动追加计费调用。

默认展示已耗时。缺少同题库历史数据时不承诺剩余分钟数；如果后来增加耗时估计，需注明估算，评分时间另算。

## 5. 完成页：先看对照，再看依据

首屏显示两个独立状态：例如「运行完成」「评分待复核」。效果摘要使用朴素文案：

- 未完成或无足够配对评分：“本轮尚不能比较答案质量；已有成本结果可查看。”
- 只有模型评分：“模型初评供参考，存在 N 个待复核答案。”
- 存在完整复核记录：“已复核部分显示……”，明确复核覆盖数，按质量、错误和成本分别描述。

首版不输出单一“有效率”、综合分或“验证通过”绿标。不用简单规则把一次耗时下降升级为稳定收益。单轮、已知回归题及演示项目范围固定显示在摘要旁。

对当前已完成的实测，页面示例应表达：

> 本轮尚未证明稳定增益。已复核的两组均为 19/20；有主干工具调用更少，平均耗时接近。范围：4 道演示回归题，每题 1 轮。

| 指标 | 无主干 | 有主干 | 差异 |
| --- | ---: | ---: | ---: |
| 检查项满足数（复核记录） | 19/20 | 19/20 | 0 |
| 额外问题条数 | 4 | 1 | -3 |
| 平均答题耗时 | 47.91 秒 | 48.58 秒 | +0.67 秒 |
| 工具调用总数 | 52 | 47 | -5 |

额外问题的条数不代表严重程度，点击可展开原文。普通代码题与业务流程等分类分别可筛选，避免总体分数掩盖某一类题变差。

评分来源可切换「模型初评」「复核记录」，默认在存在复核时选复核；不得把未复核答案的模型分数填进“复核记录”总分。两种视图分别显示可比较的题目／轮次配对数与分母。成本按双方答题完成的区组统计，质量按当前评分来源双方都有有效评分的区组统计；如果分母不同，在表下注明。

模型用量放在展开项中，答题与评审分开，输入、缓存读取和输出分别显示，不把未知计价写成实际花费。

## 6. 逐题详情与复核

逐题表展示：问题名称、类型、轮次、两组检查项得分、额外问题、工具数与耗时差、评分状态。优先提供「质量有差异」「待复核」「调用失败」筛选；完整列表始终可见。

点击问题进入详情：宽屏左右并排显示「无主干」「有主干」答案；窄屏切换组别。下方是评分项表，列出预设标准、两边答案引用、源码引用、初评判定及理由。

每项可选择「满足」「不满足」「待核查」，支持填写说明及记录额外错误；点击「保存复核」更新复核视图，不再调用模型。保留初评及历次复核，不修改原答案。复核记录注明操作者类型与时间；导入的执行助手复核不能标成用户亲自确认。

源码引用默认打开本轮冻结文件，显示行号及上下文，并注明“本轮资料”；不能静默打开已修改的当前代码。解析不到定位时保留引用文本和文档选择，不捏造链接。历史答案含临时目录时，通过本轮仓库快照映射定位。

「调查记录」展示搜索词、目标仓库、读取文件、时间顺序及工具错误。可查看主干是否注入、流程文档是否读取，但这些仅为使用记录，不标为贡献证明。首次正确定位、无关检索暂不自动评分；需要复核者判断。以后有可靠的逐题范围标注后再补充。

「重新初评」只针对已有答案，新建评分修订并保留旧版；「重新验证」新建实验批次，默认用当前项目资料，不能混称为对旧快照复跑。

## 7. 题库与历史

题库首版支持从现有 JSON 导入、查看与编辑，用户无需离开页面手改文件。每题包含问题、类型、预期检查项、适用业务范围；检查项可附依据文件／行号与事实说明，便于后续复核。

题库绑定当前项目，标记“真实历史问题／已知回归题／合成场景”。没有真实复杂项目时不自动生成复杂题并宣称已完成真实验证。模型可以协助起草题目，但首版不实现自动造题，以免把主干内容直接变成答案标准。

编辑保存产生新的题库修订；已运行批次始终保留旧题库快照。判分标准只给评分者，不给答题模型，也不写回主干。源码变更后应复核标准是否仍成立。

历史列表展示时间、题库及修订、问题／轮次数量、执行状态、评分覆盖、质量与成本摘要。可打开旧报告、导出报告、使用相同设置发起新验证。

首版只做批次内的有无主干比较，不画跨批次“持续提升曲线”。题库、代码、模型设置变化会影响可比性；页面显示这些变化信息。之后若支持新版／旧版主干对照，应在同一批次冻结相同代码与题库，只改变主干版本，而不是简单相减两次历史得分。

## 8. 当前实现与所需接入

已具备：`scripts/evaluate_backbone.py` 的对照执行和快照，`scripts/backbone_report.py` 的报告汇总，题库 JSON、逐次结果及评分记录。现有前端使用 React 与 Ant Design，哈希页签导航；后台为 Python HTTP 服务，已有问答和取消接口可参考。

尚缺：评测后台任务服务、浏览器可用的结构化进度、独立答题／评分状态、评测取消、题库编辑接口、复核接口和页面。现有脚本的终端输出多在单次答题及评分后产生，不能直接充当精确的页面阶段进度。现有综合退出码也不能直接映射成“答案失败”。

建议将评测编排抽成共享模块，命令行和页面调用同一执行逻辑，保留 CLI 入口。新增 EvaluationService 负责后台工作线程、持久化状态、事件与取消；模型调用继续通过已有 runtime，使用其取消检查能力。首版每项目一批任务、批内并发 2，不引入新的消息队列服务。

结果继续保存在 `.data/evaluations/`，任务清单及状态持久化；SQLite 可保存任务索引与状态，较大的答案／事件保留文件。复核和模型评分分层保存，汇总逻辑需新增明确的评分来源筛选，不能直接沿用“缺复核即混入模型分”的旧默认行为。

前端首版采用约 2 秒轮询批次摘要，任务结束停止轮询；详情和轨迹按需加载。后台运行独立于请求生命周期，避免持有长 HTTP 请求。复用现有管理员凭证方式管理启动、停止、题库修改和复核；已有登录状态直接使用，不新增授权步骤。前端请求工具需为新增写接口接入现有凭证逻辑。

建议接口如下（均为待实现）：

| 接口 | 用途 |
| --- | --- |
| GET /api/evaluations/setup | 当前项目、题库、主干来源和运行就绪信息 |
| GET /api/evaluation-suites | 题库列表及修订 |
| POST /api/evaluation-suites | 新建／导入题库 |
| PUT /api/evaluation-suites/{id} | 保存题库新修订 |
| POST /api/evaluations | 启动任务，返回 202 与任务编号 |
| GET /api/evaluations | 历史记录与当前活动批次 |
| GET /api/evaluations/{id} | 执行／评分状态、进度、摘要及逐题列表 |
| GET /api/evaluations/{id}/cases/{caseId}/repeats/{n} | 配对答案、评分及调查记录 |
| POST /api/evaluations/{id}/cancel | 停止该批次 |
| PUT /api/evaluations/{id}/reviews/{answerId} | 保存复核修订 |
| POST /api/evaluations/{id}/rejudge | 对已有答案创建新的初评修订 |
| GET /api/evaluations/{id}/sources/{sourceId} | 读取本批次源码快照内容 |
| GET /api/evaluations/{id}/report | 导出报告，指定模型初评或复核视图 |

创建接口接受题库编号、修订、轮次、问题子集和是否初评，由后台解析项目资料和命令；前端不用传终端命令或本地任意路径。读取失败和取消保留已完成结果。

## 9. 实施顺序与验收

第一步打通任务服务与共享执行逻辑，确保开始、进度、取消、刷新恢复和结果落盘；第二步完成页面配置、历史及逐题对照；第三步接入题库编辑、评分复核和快照查看。三步共同构成可用首版，不能停在一个启动按钮。

首版验收使用已有演示题库及必要的任务状态模拟，不为测试页面大批重复调用模型：

1. 一次点击创建一批配对验证，页面显示真实阶段和调用规模。
2. 刷新／切换页面后仍可查看该批次，不重复启动。
3. 答题成功但评分失败，答案仍可查看，质量显示待复核，不记零分。
4. 两组答案与源码快照可并排核查；保存复核不调用模型且不覆盖初评。
5. 汇总采用同题同轮和明确评分来源，分母、失败数量、未复核数量可见。
6. 停止后不再发起新调用，活动调用取消，已完成结果保留。
7. 本轮 19/20 对 19/20 的已知结果能正确呈现为质量持平、成本接近，不显示“主干验证通过”。

暂缓复杂评测平台功能：定时任务、多模型排行榜、自动造题、跨批次趋势以及图谱独立贡献评测。先使用户能从真实答案及依据判断当前主干是否值得继续改进。
