# 当前项目方案分析

日期：2026-10-13。

本记录分析当前工作区的方案与实现，提出后续改进建议；不修改现行规范。规范依据为 `docs/spec/knowledge-backbone-direction.md` 第 11 节和 `docs/spec/architecture.md`。源码已发生分包调整，本记录使用调整后的路径。

## 1. 总体判断

核心方向合理：让成熟 Coding Agent 自行调查，平台负责准确提供资料、限定工程范围、记录过程和开展对照；源码确认实现，业务补充知识解释语义，结构资料负责定位。这些边界值得保留。

当前主要问题是：问答、资料管理、资料版本和收益验证尚未形成一致的使用链路。现有能力比已经完成验证的收益多，下一阶段应优先提高资料一致性和验证可信度，再依据收益决定投入。

区分三类结论：

- **已确认行为**：从代码和本地模拟直接观察到的模式挂载、会话续用、导入状态和数据复制。
- **影响判断**：上述行为可能增加旧结论混用、错误可信度提示和运行成本；本次未用真实模型证明具体答案因此答错。
- **改进建议**：下文的资料配置、版本和发布流程是待实施方案，不能描述为当前已实现。

## 2. 值得保留的设计

1. Python 不接管问题分类、固定检索和证据推理，避免持续维护另一套 Agent 工作流。
2. 对不同工程使用独立 `ProjectContext`、数据库和资料目录，请求明确归属工程。
3. 业务补充知识按需读取，不自动注入历史项目总览全文。
4. AST 用户手动生成，问答和实验引用已有版本，不在进入页面或实验启动时生成。
5. 评测冻结资料、独立评审、区分模型初评与人工复核，失败和未评分不记零分；两组配对不受其他组失败抹除。

这些能力解决的是资料准备和实验可靠性，其功能通过不等于业务知识已经证明有效。

## 3. 优先问题与改进方案

### 3.1 普通会话缺少源码和业务资料版本边界

**事实**：`query/service.py:151-165` 只在范围、模式或 AST 版本变化时重置模型会话。`query/workspace.py:293-305` 将资料和仓库链接到实时目录。普通 `query_run` 没有保存业务资料、源码和代码地图的版本组合。

**本地复现**：在临时工程中完成第一轮问答，修改源码和业务 Markdown，再续聊；两轮传给模拟 Runtime 的 session 参数为 `[None, 'same-runtime-session']`。这证明资料变化没有触发模型会话切换，不证明真实模型第二轮一定答错。

**影响**：用户进行正常源码同步或修订业务资料后，当前读取内容和旧模型记忆可能属于不同版本。历史回答也难以准确解释它当时使用的是哪一版资料。

**建议**：由资料导入、发布和源码同步建立项目内版本号。先在会话和运行记录中保存源码、需求、业务资料、结构资料及提示词版本；资料版本变化时新建模型会话或明确切回原版本。进一步让运行引用同一个已发布资料版本，复用每次发布产生的快照，避免每道题重新复制项目。

### 3.2 日常问答配置与实验配置需要共用一套资料选择规则

**事实**：主对话只接受 `none/backbone/ast`（`query/service.py:26`）。`workspace.py:273-286` 主动将普通“有主干”模式的代码地图排除；AST 模式则排除业务补充知识。评测支持 A/B/C/D/E，并提供代码地图＋业务知识组合（`evaluation/runner.py:37-43`）。

**判断**：三组互斥配置有利于实验隔离，符合目前约定，但日常产品能力受限于实验分组。自动代码地图虽然生成，普通业务问答无法同时利用它和业务知识。这是后续产品设计建议，不能把遵循现行模式约定本身称为代码缺陷。

**建议**：以“基础资料＋可选业务知识＋可选结构导航”描述资料选择，主对话和实验复用同一份挂载规则。现有模式名称保留为兼容预设；评测用冻结的选择配置产生对照组。AST 继续引用手动版本。组合能力的默认启用与否，应依据验证结果确定，不预设两种资料同时提供必然更好。

运行时只组装资料和范围，模型继续按问题相关性决定是否读取。

### 3.3 “有原文依据”被当成“业务已确认”

**事实**：`knowledge/baseline.py:247-274` 将导入的实体、关系写为 `VERIFIED`，且置信度为 `1.0`。页面 `KnowledgeAdminPage.jsx:131` 将该状态显示为“已确认”。现有校验主要确认引用存在、名称和属性在原文范围内，并没有执行业务方确认或适用版本确认。

**本地复现**：原文写明“待核查：极优的业务定义需要确认”，通过规则解析导入后仍显示 `VERIFIED`、`1.0`。

**影响**：管理界面高估知识可信度。问答目前直接读 Markdown，因此不能声称这个数据库状态已经直接导致问答错误；但资料管理无法准确表示哪些内容仍需要确认。

**建议**：先把“已导入／引用已核对”与“业务已确认”分开。原文的待核查、冲突和适用范围应保留；由明确的人工作业确认或业务依据确认后再标为已确认。业务文档作为主要维护来源，图谱作为派生管理视图，后续修改和发布返回原文统一维护。

### 3.4 收尾已有评测，建立能指导投入的证据

**事实**：当前检索到的新资料五组正式批次为 `validation-projects/complex-loan/.data/evaluations/abcde-formal-20260909`。计划 80 次答题，现有 57 份逐次结果，其中 56 次答题完成；32 次初评完成、14 次初评失败、10 次标准无效。该目录没有最终 `results.json` 或人工 `reviews.json`。

按现有汇总函数读取逐次结果，有 10 个五组答题完成的配对块，4 个五组初评均可用的质量块。其他两组的有效配对需分别计算；不能因五组不全将它们丢弃。这些数字只描述本次找到的批次，不是全平台或业务收益结论。

**问题**：尚不能依据该批次的局部结果决定复杂图谱、固定检索或更多结构维护是否值得投入。

**建议**：先保留原答案和冻结资料，处理无效标准，独立重评并完成代表性题目的人工盲复核，再补齐确有必要的缺失配对。按题型看术语消歧、跨系统遗漏、实现正确性及无关探索，质量与成本分别报告。需要同时考虑业务文档维护成本。

评测设置也应明确冻结：模型、CLI、提示词、资料选择和执行参数。主对话与评测复用共同的读取策略；独立会话、预算和留档由评测覆盖，不把不同运行参数造成的结果都归因于资料差异。

现有“质量维度”使用评分项文字关键词分类（`evaluation/runner.py:388-394`），建议在题库中显式维护维度，而不是将这种分类视为独立的业务质量量表。

### 3.5 管理和实验准备有重复工作，复杂项目上应单独衡量成本

**事实**：知识刷新每次遍历所有 Markdown 并逐篇抽取（`knowledge/baseline.py:83-87`）；问答直接使用原文，图谱抽取不是问答的必经步骤。评测先冻结源码，再为每个答题任务复制全部仓库（`evaluation/runner.py:172-176`、`evaluation/harness.py:257-265`）。当前答题计时在任务复制与准备之后开始（`harness.py:319`）。

**判断**：实现简单，隔离清楚，小项目可以接受；大仓库和多轮实验会产生额外 IO、磁盘和管理模型调用。这些是代码确认的重复操作，其具体成本本次没有做大仓库测量。

**建议**：知识结构化只处理变更文档，按实际管理需要触发；普通问答允许直接使用合格 Markdown。评测复用一次冻结的源码视图，每个任务只创建独立工作区和资料挂载。已有只读工具策略继续使用。将资料准备、模型答题、评分和总耗时分列，避免只展示准备完成后的模型耗时。

结构导航先使用现有代码地图。AST 继续是手动可选资料版本；是否增加生成或检索复杂度，以实际定位收益决定。

### 3.6 已确认的工程结构收尾应执行，但优先级低于资料一致性

`evaluation/service.py` 当前为 1293 行，包含题库、批次、重试、复核、读取和状态持久化。按 `AGENTS.md` 已确认方向，可在现有 `evaluation/` 包内拆分题库、任务编排、复核和存储职责，避免接口之间互相耦合。

注册工程已经使用独立数据根目录；兼容单工程仍使用旧布局，根配置仍为 `baselineRoot`。按已确认的待完成调整统一项目数据布局与默认业务资料配置，使用显式迁移保留旧数据，不整目录复制历史大主干。

重复演示夹具和入口文档同步属于维护收尾。README 当前仍有旧资料链路描述，应在实施资料模式和默认配置调整时一并更新。

## 4. 推荐实施顺序

| 阶段 | 工作 | 可观察的验收结果 |
| --- | --- | --- |
| 第一阶段 | 保存资料版本，明确更新后的会话行为；修正导入状态语义 | 正常同步／更新后不会无说明地沿用旧资料上下文；待核查内容不显示已确认 |
| 第二阶段 | 收尾已有五组批次，修订标准并独立复核 | 每种题型有可核查的质量、遗漏和成本比较，结论有明确配对分母 |
| 第三阶段 | 共用资料选择规则，根据第二阶段结果决定生产默认配置 | 主对话和评测对同一配置挂载同类资料，生产组合可对应实验处理组 |
| 第四阶段 | 复用冻结资料，增量抽取，拆分服务，完成数据布局和演示来源收尾 | 准备成本可见，重复工作减少，职责和默认入口保持一致 |

优先目标是让平台对资料、版本、可信度和收益给出一致且可核查的说明，再决定更复杂的知识组织是否必要。
