# 新工程接入：架构核查与解耦建议

日期：2026-09-08。本文区分当前事实、已复现问题和建议设计；本轮未修改产品代码。知识主干和 AST 的定义继续遵循 [项目整改指导方向](knowledge-backbone-direction.md)。

## 1. 结论与目标

当前系统已经具备配置驱动的多仓库问答基础，核心查询没有依赖贷款领域的固定调查流程，但运行边界仍是一个服务实例对应一份工程配置。不能将“换配置独立启动”视为“同一平台随时接入、切换工程”。

目标应是：接入新的业务工程时，只登记代码来源、资料和项目配置，不修改平台后端、前端或通用提示词。工程可以包含多个系统、仓库和应用；工程之间独立保存会话、主干、AST、题库和评测批次。

这不意味着取消工程配置或业务知识维护。系统仍需知道哪些仓库属于同一个工程；知识主干仍需表达该工程的业务流程、职责、术语和入口。需要解除的是平台实现对某一个业务工程的依赖。

## 2. 当前事实与证据

| 位置 | 当前实现 | 接入影响 |
| --- | --- | --- |
| `project_sync.py`、`application_topology.py` | 仓库、系统、应用和源码根目录可配置 | 多仓库及单仓库多应用已有基础，可以保留 |
| `query_agent/workspace.py` | 配置驱动资料挂载，工作区目录包含工程 ID 和模式 | 核心源码调查可复用；不需要为新业务新增查询分支 |
| `query_agent/api.py:make_server` | 服务绑定单一配置和数据库，持有单一 AST、评测服务 | 没有运行中的工程注册和工程路由 |
| `schema.py`、`query_agent/service.py` | 主要数据以单工程数据库为前提；会话列表没有工程过滤 | 共用数据库换工程不是受支持的隔离方式 |
| `query_agent/service.py:_get_or_create_conversation` | 找到会话后直接更新工作区 ID；续用判断检查模式、范围、AST 版本 | 工程改变本身没有阻止旧会话续用 |
| `evaluation/ast_service.py`、`evaluation/service.py` | 默认数据根取配置所在目录下 `.data/ast` 和 `.data/evaluations` | 同目录不同配置共用数据根；只给查询工作区加工程 ID 不足以隔离 |
| `frontend/src/App.jsx` | 会话、模式使用固定浏览器存储键，API 不含工程上下文 | 同一站点切换工程需要同步切换历史、页面数据和请求归属 |
| `evaluation/service.py:_import_example` | 固定探测 `evaluations/withdraw.json` 和演示工程路径 | 示例接入约定残留在平台服务中，应改为可选题库配置 |
| `requirement/extractor.py` | 候选业务对象和流程词表包含提款、还款等预置词 | 属于需求摘要的领域偏置；不是当前主问答管线的贷款依赖 |
| `indexing.py`、`evaluation/ast_docs.py` | Java 使用专用解析器，Web 使用模式解析 | 不能把配置中允许填写语言等同于 AST 已支持该语言 |
| `start-mac.sh`、`project_sync.py` | 有项目配置的启动流程会同步仓库并调用索引 | 大仓库启动耗时与同步、解析绑定，某仓库同步失败会影响启动流程 |
| `evaluation/runner.py`、`evaluation/ast_service.py` | 实验冻结和 AST 生成均复制仓库；排除目录清单固定 | 大工程的准备时间、磁盘占用和排除策略需单独管理 |
| `evaluation/ast_service.py:_source_stamp` | 状态读取会遍历源码目录检查文件数和最新修改时间 | 大目录频繁查询状态可能产生额外开销，尚未进行容量实测 |

### 隔离复现实验

使用临时目录创建工程 A、B，两份配置位于同一目录，仓库 ID 均为 `core`，本地路径分别指向各自源码。使用模拟 Runtime，不调用外部模型、不生成 AST、不修改用户工程数据。实测结果：

1. A、B 的 AST 默认根目录相同。
2. A、B 的评测默认根目录相同。
3. A 创建会话后，使用相同数据库构造 B 服务，B 的会话列表包含 A 会话。
4. B 提交 A 的会话 ID，在模式、范围及 AST 版本均未变化时，Runtime 收到 A 的旧会话 ID。

这些结果证明共用目录、共用数据库切换配置存在隔离缺口，不代表使用各自独立目录和数据库的两个实例必然互相影响。当前真实模型的跨工程答案污染未实测，已经确认的是旧会话被继续传入 Runtime。

## 3. 建议架构：一个平台，多个独立工程上下文

先保留单体应用，不需要拆成多个网络服务。增加统一的 `ProjectRegistry` 和 `ProjectContext`，将已实现功能组合到明确的工程边界内。

```text
前端：工程列表 / 当前工程
           ↓ 请求明确携带 projectId
ProjectRegistry：登记与解析工程配置
           ↓
ProjectContext：配置、数据库、资料目录、源码版本、能力状态
           ├─ QueryService / WorkspaceManager
           ├─ KnowledgeService
           ├─ SourceService / SnapshotService
           ├─ AstService
           └─ EvaluationService
```

建议第一阶段采用“一工程一数据库、一工程一数据目录”，最大程度复用现有表结构。平台登记库只保存工程元信息，不保存各工程的知识和问答内容。

```text
平台数据目录/
  registry.json
  projects/
    <projectId>/
      project.json
      knowledge.db
      knowledge/
      requirements/
      workspaces/
      ast/versions/
      evaluation-suites/
      evaluations/
      snapshots/
```

源码允许引用外部本地目录，也允许由平台同步 Git 仓库。不得要求把新业务工程复制进平台源码目录。所有服务从 `ProjectContext` 获取路径，不再各自根据配置父目录猜数据位置。

工程 ID 是登记后的稳定身份，展示名称可修改。请求、会话、AST 版本、批次和后台任务都明确记录所属工程。收到其他工程的会话或版本 ID 应拒绝，不能通过改写工作区归属将记录移到当前工程。

## 4. 新工程接入流程

1. **登记工程**：名称、仓库来源及路径；可导入现有配置。已有本地源码可直接接入，无需创建虚假的 Git 地址占位。
2. **检查资料**：显示哪些仓库可读、哪些尚未拉取、识别到哪些语言和应用。区分工程、系统、仓库和应用四个概念。
3. **开始问答**：源码可读即可使用无主干模式；索引、主干、AST 和题库均不是基础问答的前置依赖。
4. **补充主干**：独立导入或维护项目总览与业务流程。尚未准备时明确显示未配置，不能宣称已获得主干增益。
5. **手动生成 AST**：显示语言覆盖与预计处理范围，由用户点击生成并引用版本。不支持的文件仍可供源码问答，页面提示结构资料覆盖不足。
6. **导入题库并实验**：题库属于当前工程，示例题库由工程配置显式声明；三组实验各自显示就绪状态，AST 缺失时引导到手动生成页面。
7. **切换工程**：历史、资料、主干图谱、AST 和实验页面一起切换；正在运行的任务仍绑定原工程，不能将迟到的结果写到新工程页面。

工程切换应体现在页面 URL 和请求中，例如 `/api/projects/<projectId>/...`。浏览器会话存储按工程分区。不要只用可变的全局“当前工程”变量决定后端请求归属，因为两个浏览器标签页可能同时查看不同工程。

## 5. 大工程需要额外解耦的能力

### 源码与索引

服务启动只加载已登记状态。Git 同步、代码索引成为独立任务，显示进度和失败仓库。问答直接读取已准备好的源码，管理索引暂不可用不阻塞源码问答。

统一配置扫描范围、排除目录和生成产物规则，并明确这些规则影响问答可见资料还是只影响索引。不能为了实验快而偷偷删去对照组正常资料。已有 `applications.sourceRoot` 可继续作为模块元数据，但当前查询范围主要到仓库级，单仓库大工程还需补应用/模块选择能力。

### 结构解析

将现有 Java、Web 解析器放在同一能力接口后。页面显示实际解析语言、未支持文件和解析失败，不以一个“生成成功”状态代表全工程覆盖。接入新业务不应需要写解析器；新增语言支持则可能需要独立适配，这两种工作必须区分。

### 资料与实验快照

把源码解析、快照准备和资料版本读取移出评测编排模块。当前 AST 服务引用 `evaluation.runner.resolve_project_sources`，主查询又引用评测目录下的 AST 服务，属于职责耦合；迁移为通用项目资料服务后，评测仅负责题库、模式编排、评分和报告。

同一批次各组继续使用一致冻结资料。后续可以让 AST 和多个实验引用同一不可变源码快照，减少重复复制；不能用指向可变工作目录的链接代替冻结快照。先测实际工程的准备耗时和磁盘量，再决定增量快照优化，不必先引入复杂存储系统。

源码变化检查移到同步完成通知或独立刷新任务，页面轮询读取缓存状态。只标记 AST 待更新，永远不在状态检查时生成 AST。

## 6. 建议实施顺序

### 第一阶段：统一工程边界

- 引入工程登记、统一配置解析和 `ProjectContext`。
- 数据库、工作区、知识、题库、AST 和实验统一归属于工程目录。
- 后端按工程路由，校验记录归属；前端增加工程登记/选择，并按工程维护会话和请求状态。
- 当前贷款验证工程作为普通已登记工程迁入；保留旧批次、AST 和查询记录，不能混合归属不明的历史库。

这一阶段的完成标准是“不改平台代码接入第二个不同领域的工程，并能来回切换问答”。

### 第二阶段：去掉非必要前置条件和样例约定

- 同步、索引与服务启动解耦，缺少主干/AST 时仍能进行无主干问答。
- 示例题库改为配置项；领域候选词改为工程可选配置或通用抽取能力。
- 将 AST 与源码快照能力从评测目录移出，统一资料解析入口，消除问答和评测分别解释同一配置的问题。
- 明确不同语言的结构支持范围，补应用/模块范围选择。

### 第三阶段：按真实大工程数据优化

- 测量登记至可问答时间、同步/索引/AST 时间、实验准备时间、磁盘占用和状态接口耗时。
- 按测量结果改进扫描裁剪、后台任务、快照复用和结构文档分片。
- 大工程回答质量另用真实题目验证；不能用架构解耦完成或测试全绿替代质量验证。

## 7. 核心验收场景

1. 新接入一个非贷款工程，只新增登记信息、源码引用及可选资料，平台代码没有变更；不准备主干与 AST 也能问答。
2. A、B 使用相同仓库名和案例 ID，各自历史、知识、AST 和批次互不覆盖；B 不能续用 A 会话。
3. 两个标签页分别打开 A、B；A 有运行中问答或实验时切换到 B，返回结果仍属于 A。
4. 重启服务、进入页面、切换模式和运行实验均不生成 AST；只有手动操作创建版本。
5. 新工程含当前未支持的源码语言，源码问答仍可使用，AST 页面如实显示支持范围。
6. 在选定真实大仓库上测量准备成本；一次实验的各组引用一致源码与资料版本，重试保持原冻结输入。

本轮只验证了第 2 类问题在现状中确实存在，未宣称目标架构已实现，也未进行大工程性能或真实模型效果验收。
