# 契约与返回字段索引：第一阶段实现（2026-10-31）

## 当前结论

已接入现有 LangChain 1.2 Agent 的实验分支，默认关闭。本地机制回归通过，获批的两版 Qwen 真实调用也已完成，共 16 次请求，无重试。两版均正确识别渠道完整对象透传；普通收尾仍有层次混淆和过强建议，结构收尾则缺少业务解释，**整体问答尚未通过验收**。

结构事实正确不等于整体问答正确。当前专用收尾只渲染结构事实并选择业务原文，限制了自由业务概括；必须同时检查它是否漏掉状态条件与改动建议，不能仅凭阻止了一个错误就宣称整体变好。

## 已实现

- `codeintel/contracts/`：显式解析 Spring Controller、RestClient 默认配置绑定、返回调用、字面量 Map／列表、普通 record 构造及字符串 switch。HTTP 连接同时核对服务身份／端口、方法和路由；歧义与不支持项保留为缺口。SQLite 保存工程、索引版本、源码、结构与证据；修改文件重解析，未变文件复用，删除移除，记录 Git diff 行范围。
- `FindCapability` 是 BM25 导航；`TraceContract` 和 `TraceResponseFields` 交付原文、关系、字段和缺口。不是完整业务语义图，也没有新增向量模型下载。
- 具体缺口自动形成 Read 待办，不依赖模型调用 Investigation。补读状态自动更新为 `source_read`，不将补读冒称关系已证明，也不在问答中重新解析 AST。
- 字段证据包按完整事实及所需原文接纳，默认 16,000 字符／260 行。相关文件变更或不在当前仓库授权范围时，不交付依赖该文件的字段。程序在无工具收尾前再次核对。
- `CONTRACTS=on` 与 `ANSWER_MODE` 独立：`plain` 用于单独测试检索工具；`contracts` 用于附加结构事实收尾。默认仍为关闭／plain，未修改用户 `.env`。

## 源码本地核对

显式准备范围为 `channel-service-repo`、`loan-middle-repo`、`external-simulator-repo`，共 64 个文件，其中 61 个 Java 文件，29 个 HTTP 入口，无 Java 语法错误。未解析状态不包含在这个错误计数中；不是宣称全部接口已理解。没有索引 Fineract、Mifos 前端，也未生成 AST 管理页版本。

已知开发题 `v2-channel-display` 的首个入口候选为渠道 `GET /api/drawdowns/{channelRefNo}`。其字段证据包含 15 个字段、44 行原文、约 13,007 字符，当前所需返回链没有结构缺口，确认包括：

- `middleStatus`、`displayStatus`、完整 `detail`。
- `detail.payments[].status`。
- `detail.booking.status`、`detail.booking.retryCount`。
- `displayStatus` 输入绑定 `middleStatus`／`detail.status`，SUCCESS／FAILED 保持原值，其他值映射 PROCESSING。

这只是源码结构诊断，不是模型答案或独立保留题结果。字段存在不能证明页面消费、TO_BOOK 就是失败，或保证只改一处收益最大。机器记录见 [源码核对证据](contract-index-source-review-20261031.json)。

## 真实模型验证方案

使用同一已知开发题与 `.env` 的 Aliyun qwen3.8-27b，文件工具与正常资料全部保留：

1. 增加契约工具，`answer-mode plain`。
2. 相同工具，`answer-mode contracts`，额外限制结构事实的最终表达。

每版最多 8 次请求（最多 7 次调查＋1 次独立收尾），每次输出最多 2048 token，消息正文最多 64,000 字符，标准工具定义另计；非思考、温度 0、失败不重试、不传参考答案。共最多 16 次，接口无金额硬限。用户另行批准本批两版复验，实际各 8 次、共 16 次，授权已用完。

比较字段断言、展示／完整响应的区分、失败与等待的业务条件、页面证据、建议的条件和遗漏，再记录用量与时间。历史 v4 文件结果仅供诊断，不是本次新配对文件基线。该两组只能区分增加最终约束的效果；整体检索收益还需要新文件基线、独立问题与保留题。

## 真实结果与轨迹判断

| 结果 | 契约工具＋plain | 契约工具＋结构收尾 |
| --- | --- | --- |
| 请求数 | 8 | 8 |
| 累计输入／输出 token | 69,398／2,407 | 76,018／540 |
| 耗时 | 58.878 秒 | 34.778 秒 |
| 最大消息正文字符数 | 35,927 | 38,081 |
| 最终请求字符数／最终输出 token | 16,608／1,967 | 31,969／70 |
| 对象透传、付款／记账状态字段 | 正确识别 | 程序准确输出 |
| 业务解释与建议 | 层次仍混淆，收益判断过强 | 业务原文丢失，解释不足 |
| 整题通过 | 否 | 否 |

两条调查轨迹均为 `FindCapability → TraceResponseFields(C5) → Read(ChannelService) → Grep(中台状态) → Read(DrawdownService) → Grep → Grep`。没有结构缺口，所以没有真实运行中的自动补读任务；自动补读收益仅有本地模拟验证，不能以本批宣称其减少了调查遗漏。最后仍搜索了属于 Fineract 的 Mifos 前端，不能用它补齐未登记的渠道消费端；这也没有带来有效页面证据。

普通版已明确列出 `middleStatus`、`detail.payments[].status`、`detail.booking.status` 和 `retryCount`，此前“仅返回 displayStatus”的字段误判消失。但句首仍说“当前渠道接口不能直接区分”，随后又承认“后端数据层面具备区分能力”。准确层次应是完整响应有字段、单一 displayStatus 有合并、页面使用未确认。

普通版推荐 `displayOf` 收益最大，证据也不足。把 `EXTERNAL_SUCCESS_BOOKING_PENDING` 单独显示只能区分外部处理与入账阶段，不能独自区分正常 TO_BOOK 和 RETRY_NEEDED。它最后承认需要已有 detail 字段以及前端契约条件，但没有这些消费端证据，不能保证某一处改动收益最大。

结构版的最终 JSON 正确选择 C5 和三段业务原文。其中 `S32:188-242` 是已经读取的 55 行成功处理／book 异常分支，却被单段最多 12 行的程序规则整个丢弃。没有发生上下文截断：记录 `omittedBlocks=0`。这次缺失是装配策略造成，不能归咎于模型没找到代码。

修复后每段优先短引，但按**业务原文总计 72 行**控制，不再仅因单段超过 12 行而删除已交付的分支上下文。审计记录区分模型提出数量、实际接纳数量与行数。用原始冻结请求／响应做本地复放，三段、66 行全部接纳，问题列表为空，**新增模型调用 0 次**；不覆盖原始真实结果，不冒称修复后的新模型复验。新增回归及相关收尾测试共 34 项通过。

即使恢复这些代码片段，当前结构版仍主要输出字段、映射与源码，尚未把它们组织成足够清楚的业务判断和改动选择。不能通过收窄答案来宣布整体优于普通版，也不能把更低输出 token／耗时解释为图检索带来的成本收益。结构版累计输入反而约多 9.5%，包括收尾中的结构证据包与原文重复。

## 下一步依据

保留契约／字段索引这一已跑通的机制，暂不切换默认。后续应让程序先组织业务待证事项（完整数据、展示投影、实际消费者、状态条件与改动前提），将源码绑定的结构事实带入解释和建议，而不是继续添加一个可选大计划，也不是永久退化为大段源码引用。业务语义层需对确实缺失的术语、状态边界和隐式关系补充短依据，不能把代码能确认的完整流程复制到知识主干。

现有引用装配修复可用冻结结果验证；更改后的语义答题器需要新的真实配对和独立题，本批授权不续用于后续调用。

## 未完成范围

契约入口选择仍由模型在候选中进行。自动补读解决具体未解析边的读取调度，不保证模型已经识别所有业务疑点。Kafka／GraphQL、Feign 补充、任意 DTO 序列化、数据库状态转换和完整控制流、业务语义实体链接、消费端与 UI 证明均未由本阶段实现。定时任务只在显式结构记录中保留标记，未输出“定时补偿一定完成”的推断。复杂动态 URL、反射和修改后的可变对象保留未解析，需回到源码。

先验收窄范围行为和真实答题，再决定扩展语义层或全量图；没有新增图数据库、页面或默认开关。
