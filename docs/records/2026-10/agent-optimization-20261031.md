# Agent 工具、导航与调查状态优化（2026-10-31）

## 本轮结果

已修复轨迹中可复现的 Glob／Grep 问题，补入工程职责导航、搜索状态交接、公开请求／响应快照，并实现可选的调查队列。真实 Agent 回归在相同八次请求预算下补读了此前遗漏的 MiddleClient 与渠道 Controller，没有再转去 Mifos 前端扩搜。

**答案质量仍未达标。** 首段声称页面／接口只返回 displayStatus，正文又引用 middleStatus 和完整 detail。这个具体断言与返回代码不一致；不只根据“不能直接支持”的歧义标题判错。模型还只创建了待办，没有持续更新其引用和状态。因此默认启用工具修复、导航与搜索状态交接，调查队列保留为 `WORKFLOW=tracked` 实验选项，默认 `basic`。答题模式仍默认 plain，facts 未通过的历史验收不变。

这不是新保留题或人工验收；为已知开发回归，由助手复核，`humanReviewed=false`。改善了部分调查动作，不能等同于完整调用链或最终答案正确。

## 修改内容

### 文件工具

- Glob 的 `**` 支持零层及多层目录，兼容 Python 3.11，不依赖较新版本 pathlib 的 full_match。
- `Glob(pattern="repos/*", kind="directories")` 可明确发现仓库目录，不再用文件结果猜测目录是否存在。
- Grep 默认区分大小写，支持 `case_sensitive=False` 与 `whole_word=True`；避免状态枚举 PROCESSING 被普通英文 processing 挤占结果。
- 根目录路径规范化，不把 `repos/<id>/.` 当成文件对象。

### 工程职责和交接

WorkspaceManager 从当前工程配置生成 `.codeagent-project-navigation.json`，只记录系统、应用、仓库、源码范围与类型，不复制业务实现或凭名称推断关系。运行时按本轮授权仓库过滤导航，并核对工程 ID。导航变化和工作流模式变化不续用原模型上下文。

调查和最终答题均接收配置中的职责及本轮搜索状态，包括未命中、错误、截断与已读位置。状态只约束结论范围，不被当作实现证据。完整代码原文依旧来自 Read／SearchCode，未确认的消费者不能被其他系统唯一的前端替代。

### 可选调查队列

`Investigation` 接收当前问题的对象文件、核心待办、端点引用和明确补读位置。程序在同一批工具全部完成后核对更新，避免任务声明与并行 Read 的完成顺序影响检查。明确 next_read 后由 before_model 执行配对 Read，不占新的模型请求，并标记事件 origin=workflow。

任务引用只能来自本轮实际交付原文；符号必须出现在所引行范围。关系需不同文件／符号端点，consumer 需已登记前端的代码引用。目录可以作为初步搜索范围，但不能取代文件与符号端点；本地修正了目录范围和引用文件的匹配方式。

关键开放任务存在时，提前答案会退回调查；预算结束后交接并保留未确认项。unavailable 需要说明资料缺口，不能等同于实现不存在。任务 supported 仅表示所列原文端点已读，不证明连接语义。规划仍由模型提出，不会自动发现全部关系；这一限制在本次真实运行中仍明显存在。

### 逐轮可复核记录

工作区 `.langchain-traces/` 保存系统／用户／工具公开消息、工具定义、公开响应、用量和调查状态；不写认证信息或模型私有思考。记录的是供应商序列化前的 LangChain 输入，不冒称 HTTP 原始报文。被退回的公开草稿保留在快照，不作为最终答案发送。

`evaluate_langchain.py` 新增 `--workflow-mode basic|tracked` 和 `--trace-output`，在临时工作区清理前复制快照，失败时已有调用快照也可保留。结果不覆盖旧运行。

实际轨迹：

1. 第 1 轮创建三项调查待办，并在渠道 Grep。
2. 第 2–3 轮读取渠道 Service 两个区间，取得响应与展示映射。
3. 第 4 轮检索中台状态并列出渠道 Java 文件。
4. 第 5–6 轮读取中台 Service 两个区间，取得返回字段与入账状态处理。
5. 第 7 轮并行读取 MiddleClient 和 ChannelController。
6. 第 8 轮无工具答题，收到职责、搜索状态、开放待办与已读原文。

真实运行中只调用一次 Investigation，没有提交 next_read 或后续任务完成更新，所以程序自动补读和提前答案退回**仅通过本地测试，未在这次真实运行中触发**。它也没有读取中台 Controller，不把此轨迹叫作完整 HTTP 链路已核实。

最终答案开始承认没有渠道前端资料，避免了旧答案关于前端 fallback 的确定性保证；但开头仍说接口只返回展示状态，随后又引用了完整 Map 响应。答案还引入了未确认的 BOOKING 枚举作为建议条件。核心事实综合与建议依据仍需要改进，不能仅以多读两个文件认定整体通过。

调查待办始终开放说明：提供任务工具并不保证模型维护状态，宽泛的“渠道／中台／外部流转”任务也未变成明确的待补读连接。这是该队列仍留实验状态的原因；当前不继续增加未经授权的调用来修饰结果。

## 为什么错误仍能流出：快照进一步核对

重新核对第八次真实请求，而非只看最终答案：收尾消息 36,671 字符，供应商报告输入 10,671 token；原文块遗漏为 0。渠道返回的 middleStatus／完整 detail、中台 payments 与 booking 的构造均明确存在于该次输入，最终回答也引用了这些代码。模型输出 1,528 token，没有达到本轮 2,048 的设置上限。关键反证在应用交付层没有缺失，不能把“接口只返回 displayStatus”的断言解释为这些代码没有给到或输出额度不够；这不代表所有业务与页面资料已充分。

可观察的错误归纳是把“展示值合并、没有单独的处理中原因字段”扩大成“接口没有可区分的数据”。源码支持的三个结论应分别是：完整响应已有可进一步判断的状态数据，displayStatus 单独不足，页面是否消费这些数据未确认。字段是否顶层独立、是否被赋予运营文案、是否已经返回属于不同判断。

程序没有拦住它，有三个明确原因：

1. 本次 answerMode=plain，第八次请求直接生成自由答案，没有执行 facts 的有限核对；已知的 facts 实验也尚未证明能够稳定解决对象归属与引用问题，不能简单切换后就宣称修好。
2. 调查队列管理的是待办而非已接受的事实表。三项任务只有宽泛目标，refs 始终为空；真实模型只在第一轮调用了一次 Investigation，没有更新完成状态，也没有提供 next_read。所以自动补读和提前答案退回都没有实际触发。
3. 前七次公开响应都是工具调用，没有提前的纯文本答案。程序在调查配额用完后进入独立 compose，这条正常的预算收尾路径仍允许在两个关键开放任务存在时生成自由结论。qualify 只在答案末尾追加未确认说明，不检查或撤回首段的错误事实；提示保留缺口不等于程序限制了结论。

因此，上轮修复改善了工具与调查路径，但没有建立“返回对象／字段／透传连接 → 可作出的结论”的约束。当前机制可以提醒缺口，不能保证最终答案使用证据一致。91 项本地测试证明补读、状态交接、预算与快照按设计运行；预算交接测试没有证明最终语义断言正确，不能把测试数视为问答已修复。

关于“只创建了一次计划”：创建一次本身正常，缺失的是后续证据与状态回填。逐轮快照确认第 2–7 次请求仍包含“核对后用引用更新同一任务”的系统提示和 Investigation 工具，不是提醒或工具从上下文消失。当前封装将 Investigation 与文件工具并列供模型选择；Read 结果只写入原文目录、已尝试读取位置和 observations，不自动回填 task.refs/status。继续读取也不要求先提交状态更新；只有模型主动选择 Investigation 才会更新任务。前七轮持续选择工具，因此关键任务检查的“提前纯文本答案”分支未触发；第八轮已是无工具收尾，无法再调用任务更新。可确认的是缺少必经的状态回填阶段，不能从记录断言模型究竟是遗忘、误解还是更偏向选择文件工具。下一步应由程序登记当前任务与读取结果，在关键节点调度事实／缺口核对；不强制反复重写整份计划，也不把读到文件自动判成业务已证明。

更深的模型层原因仍是待验证推测：原题“直接支持”的歧义、长上下文、非思考设置或模型本身都可能影响归纳，现有实验没有逐一隔离。同一 Qwen 在先前一次固定证据结构输出中曾正确提出“渠道已透传所需字段”，但当时上下文与格式也变化，不能单独归因于格式，更不能宣称开思考或换模型必然解决。

下一步应优先验证小范围的返回契约：以真实文件／符号锚定接口对象，记录字段生产端与透传连接，接口数据、展示映射、页面消费分开得出结论；没有连接依据时保留未确认。最终文字不能重新发明与这些事实相反的总断言。任意业务语义仍需模型解释和独立复核，这个约束也不能被称为通用代码语义证明。本段仅补充诊断，没有新增模型请求或修改运行时代码。
