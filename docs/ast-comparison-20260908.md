# AST 对照方案与验证（2026-09-08）

本方案遵循知识主干整改方向。AST 是代码结构导航，不等同业务知识图谱；目标是测量结构信息的增量作用，不以文件生成成功或读取次数证明有效。

## 五组设计

通过 `--comparison diagnostic_ast` 或页面“五组诊断”启动：

| 组别 | 与各组相同的资料之外，额外提供的内容 |
| --- | --- |
| code_only | 无；保留正常源码、README、需求 |
| overview | 人工业务总览，自动注入 |
| optional | 同一人工总览＋按需流程主干 |
| ast | 机械生成的 AST 结构总览，自动注入；结构索引按需读取 |
| overview_ast | 与 overview 相同的人工总览，附结构资料入口；按需读取 AST；不提供人工流程主干 |

报告分别比较 AST 对无主干、总览＋AST 对仅总览、总览＋AST 对完整主干。每项增量使用各自成功且有评分的配对分母。`abc` 仍支持无主干／完整主干／AST三组，旧批次保持原样；新 AST 生成器版本记为2，不把它与旧无导航版本直接混算。

`overview_ast` 的总览末尾增加一条结构入口，因此测量的是“提供可发现的结构资料”的整体增量，不能称为完全等长提示实验。

## 生成与接入

输入仅是冻结源码和原配置中的仓库标识，不读取题库评分项、人工主干或需求来生成结构图。

- Java 使用现有 tree-sitter 索引；Web 使用现有模式解析，不能统称全部是完整 AST 解析。
- 主源码按仓库、模块/源码根、包与类型分组。
- 类型显示源码路径及行号；方法显示行号，超过40个明确提示截断。
- HTTP静态注解端点按类前缀＋方法路径展示；Feign等调用条目保留事实类型，不当成已验证跨系统调用链。
- 修正方法端点挂在方法名下却只从类名取端点导致的遗漏；类型以文件路径和限定名称共同区分。
- `project-overview.md` 只列仓库及结构索引入口，自动注入；`ast/repo-N-index.md` 导航到结构分片。
- 结构分片按类型边界，目标每片240行或16000字符；单个类型块不拆散。类与方法过多时按需检索分片，不一次注入全量。
- 各 AST 组共用一次机械生成结果，避免为同一冻结源码重复生成。

不要求每题强制读取 AST。对无需结构地图就能直接定位的问题，应允许模型直接读源码；读取为零时，只能解释为未观察到按需地图使用，不能认定其内容无效。

## 成本与证据

`protocol.json/referencePreparation` 记录 AST 生成耗时、生成器版本、各组文档数/字符数/自动总览字符数。生成成本不计入答题耗时，但在报告单列。

每份新答案的 `referenceUsage` 记录：

- `overviewInjected`：实际命令是否包含总览正文。
- `astContentCalls`：成功读取或在 AST 指定目录中检索正文的次数，不把 Glob 列目录算作读取。
- `referencePathsAccessed`：实际访问资料的路径。

旧答案无该字段时显示“未观测”。页面逐题轨迹和导出报告显示接入记录。跨整个基线目录的搜索可能涉及AST，但不盲目归因于AST；需结合完整轨迹核对。

调查记录还修正了工具时间采集：优先使用带实际相对时间的事件回调，避免运行时返回的无时间事件覆盖计时轨迹。

## 验证入口

```bash
.venv/bin/python scripts/evaluate_backbone.py \
  --suite validation-projects/complex-loan/evaluations/complex-loan-diagnostic-v3.json \
  --comparison diagnostic_ast \
  --cases v2-approved-limit biz-payment-pending \
  --repeats 1 --judge --workers 2
```

两题五组单轮共10次答题、正常10次初评；只用于流程和方向观察，不是稳定收益证据。再按题型增加样本、固定设置重复，不能选出有利题目后泛化结论。

本次真实执行目录：`validation-projects/complex-loan/.data/evaluations/ast-diagnostic-pilot-20260908`；历史修订标准重评目录：`validation-projects/complex-loan/.data/evaluations/diagnosis-rejudge-20260908`。答案、冻结资料、调用轨迹与初评依据均保留；不修改原批次。

实测批次在启动时冻结了214份 AST 文档（含总览、5个仓库索引和208个结构分片），约235万字符；总览590字符。准备耗时76.823秒，内部导航链接核查无失效。启动后发现分片上限计算未包含标题和段落分隔符，已修正并补测；本批次保留启动时资料（最大323行、16225字符），不在实验中途替换输入。后续批次按完整文档计算240行/16000字符目标，单类型块超长时仍不拆散。

模型身份按每次返回的 `metadata.reportedModels` 留痕；本地网关返回的模型标签不等于已独立确认的实际上游模型。超时、预算上限与评分格式失败按未评分处理，不以零分参与质量比较。

实测暴露总览链接的可用性干扰：`overview_ast` 首题第6步访问未配给的 `credit-limit-flow.md`，第8—13步继续枚举或搜索基线目录；AST正文访问为零。总览中的这些文件链接在消融组不可用。已在后续生成的 `overview` 与 `overview_ast` 总览后追加相同资料范围说明，保留同一业务正文并明确转向源码。本次冻结输入没有该说明，其额外工具成本不可直接归因于 AST 内容复杂度。

| 题目 | 无主干旧→新 | 完整主干旧→新 | 旧版AST旧→新 |
| --- | --- | --- | --- |
| 策略码 | 2/5→4/5 | 2/5→4/5 | 2/5→3/5 |
| 迟到FAILED | 4/5→0/5 | 5/5→3/5 | 2/5→3/5 |

策略码旧评明确写出“源码与标准矛盾，按规则不给分”，说明评分口径确实曾惩罚正确答案。迟到FAILED的无主干答案则断言终态闸门完全防护，未处理补偿任务持有旧实体的并发时序，新评指出了这个遗漏。完整主干与旧AST在这两题分别合计7/10、6/10，无主干4/10；这只是相同旧答案在修订标准下的初评，不是新主干接入后的收益，更不能与本轮新版AST直接合并。并发题仅完整主干完成4/5，其余两组未评分，不作配对质量比较。

## 新版AST五组实测结果

两道题、每组一次，共10份答案全部生成；8份完成模型初评，2份评审超时。评分均为自动初评，不是人工真值。

| 组别 | 授信细节题 | 付款处理中业务题 | 两题答题总秒 | 工具调用总数 | 资料正文访问 |
| --- | --- | --- | ---: | ---: | --- |
| 无主干 | 5/5 | 5/5 | 149.46 | 23 | 0 |
| 仅总览 | 5/5 | 未评分：超时 | 132.17 | 26 | 0 |
| 完整主干 | 5/5 | 3/5 | 119.25 | 13 | 2次人工流程 |
| AST | 4/5 | 5/5 | 96.29 | 22 | 1次仓库结构索引 |
| 总览＋AST | 5/5 | 未评分：超时 | 166.85 | 36 | 0 |

**本轮未证明主干或AST的稳定收益。** AST与无主干两题均有评分：9/10对10/10，少53.17秒、少1次工具调用；另有76.823秒一次性结构资料准备成本。若把本批次全部生成成本计入仅这两次AST答题，总时间约173.11秒，反而高于无主干149.46秒；不能忽略准备成本或假定已充分摊销。两题单轮的时间还受模型响应波动影响。

完整主干确实被使用，工具调用13次少于无主干23次，但得分8/10低于10/10。业务题漏掉渠道详情的 `detail` 透传、回调与主动查单共用 `onPaymentResult` 两项要求；因此不能把省调用解释成既有质量下的确定收益。授信题AST漏的是模拟服务与中台生效职责边界，不是算错额度。

首题轨迹经 assistant 复核，各组都在第1或第2步检索出 `CreditService.java`，后续源码确认其承担额度生效逻辑。该题核心类本就容易定位。此处只标注首次核心类定位，无关检索与所有业务遗漏仍保留待复核，不把首次 Read 或空搜索直接分类。

仅总览与总览＋AST业务题未评分，二者质量增量只能比较首题，不能把另一题记成零分。混合组在本轮仍受到缺失流程文档链接的干扰；后续已增加范围说明，但尚未用真实模型重跑该修正，不能宣称问题已在行为层验证消除。

### 观测数据修正与验证边界

本轮发现 `/var/folders` 与 `/private/var/folders` 指向同一目录，但原访问统计直接作字符串路径包含判断，漏认了AST仓库索引读取。现已按规范化实际路径匹配，并增加符号链接回归。依据已保存的 `events.jsonl` 重建工具时间、重算资料访问，保留运行时实际命令的总览注入判断，未更改答案或初评。修改前后的计数留存在批次的 `observation-corrections.json`。

本地验证：31项后端评测测试通过，8项前端测试通过，前端生产构建通过，Python 3.11语法兼容核查通过，`git diff --check` 通过。源码分片长度与总览范围提示的后续修正仅完成本地回归；本轮模型输入仍是启动时冻结版本。
