# Agent 开发实践中的问题与思考

近期通过 Vibe Coding 开发了一些 Agent，实际使用中仍会出现回答遗漏、判断缺少依据等问题。换用更强的模型后，部分问题得到解决，部分依然存在。结合《深入理解 AI Agent》的阅读，开发中的关注点也逐渐清晰：怎样提供合适的信息，怎样把必要规则落实为程序行为，怎样根据真实运行结果改进系统。

跨系统源码问答平台是其中一次实践：Agent 按问题搜索、读取多个工程的源码，再组织回答。围绕模型配套的工具、上下文管理、程序约束和反馈机制，构成了这里的 Harness。

## 一、大代码库下的上下文管理

首先遇到的是信息量与上下文容量的矛盾。代码库往往很大，即使模型支持更长的上下文，一次装入全部源码也会增加成本，并混入大量与当前任务无关的内容。开发时需要解决的，是每次调用究竟应当提供哪些信息。

项目采用按需读取的方式：先提供工程目录、职责和简短索引，通过 Glob 按文件名查找、Grep 按文本或正则表达式定位，再用 Read 读取相关源码。返回内容保留行号、截断提示和续读位置，便于模型继续查证。另有按函数、类组织的混合检索作为可选增强，索引由显式操作准备。

随着工具结果和对话历史增加，还需要控制上下文的累积。当前按预算回收旧工具正文，保留工具调用与结果的配对；源码变化后让旧原文失效，需要时重新读取。同时增加搜索状态交接，保留未命中、截断等信息。项目资料长期保存在工程中，工具原文按预算管理，当前目标和未确认事项则需要持续交接。这里的取舍是：减少历史体积时，还要保住任务继续进行所需的线索，不能只按文本长度截取。

## 二、模型判断与程序约束的分工

另一个问题是，写进提示词的要求，并不一定会被执行。对于计算和可明确判定的规则，可以由模型理解问题，再交给代码计算或校验；开放性的分析仍需要模型完成。这样分工，才能把需要稳定执行的要求落实到程序中。代码辅助推理也有同样的前提：模型必须先把问题和条件表达正确。程序可以精确执行已有规则，却不能仅凭执行成功发现规则遗漏了某个业务条件。

项目已将读取范围、调用次数和运行时间交给程序管理，也尝试在事实整理模式中核对引用是否来自实际交付的原文、行号是否有效。但程序能按既定逻辑执行，并不代表规则表达和模型输入一定正确：引用检查通过，仍不能证明模型对源码的解释正确。事实整理实验还存在归属和引用遗漏问题，尚未成为默认答题方式。

这也使模型与 Harness 的分工成为需要实测的取舍。更强的模型可能减少某些提示和步骤编排，但预算、来源范围等明确规则仍适合由程序执行。某项校验有没有收益，需要放到具体模型和任务下比较，不能直接照搬其他实验的结论。

## 三、根据失败轨迹改进 Harness

仅看最终答案，很难判断失败发生在哪一步。项目因此增加逐轮记录，保存实际提供给模型的消息、工具参数、返回内容和调查状态。复盘发现过两类具体工具问题：目录中已有文件，递归匹配却返回空结果；搜索状态枚举时，普通英文文本挤占了结果。针对这些问题，已修正 Glob、Grep 的匹配语义，并补充工程职责导航和搜索状态交接。

但一次真实回归中，虽然多读到了关键文件，答案仍然出错。记录还显示，模型只在开始创建了调查计划，后续没有更新状态，而要求更新的提示和工具始终存在。计划工具只是提供了记录安排的能力，读取结果是否回填、收尾时是否使用这些状态，还取决于后续流程。这个问题不能再靠多写一句提示来认定解决：后续应在必要节点由程序调度状态核对，把读取结果、未完成项和最终答题衔接起来。当前调查队列仍是实验能力，不能把部分调查动作改善当成答案质量已经达标。

因此，轨迹分析应服务于“定位失败—修改机制—同题复验”。模型可以辅助分析，但效果要由新的运行结果确认。后续若引入提议者—审核者分工，双方应共享验收标准，审核者只看当前结果和相关证据，调查者接收具体反馈。这样分开上下文的收益，以及新增模型调用的成本，也需要实际比较。
