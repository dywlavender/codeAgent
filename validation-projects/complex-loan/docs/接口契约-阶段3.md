# 阶段 3 接口契约（授信与多层额度）

定稿日期：2026-09-06。依据：[三系统边界设计](三系统边界设计.md)、[主设计 §四/§六/§八](../../docs/knowledge-backbone-direction.md)。阶段 2 契约（`接口契约-阶段2.md`）继续有效；本文只写新增与变更。

## 1. 多层额度模型（中台实现，唯一裁判）

一笔提款同时受多层约束，**可用额度取各层余量的最小值**，层与层不能相加或互相替代：

| 层 | 余量口径 | 说明 |
| --- | --- | --- |
| 企业总授信 | `totalLimit − occupied − preOccupied` | 单个授信的总额度 |
| 产品子额度 | `subLimit − occupied − preOccupied`（按 productId） | 未配置的产品层不参与约束 |
| 集团限额 | `groupLimit − occupied − preOccupied`（集团全部成员共享） | 关联企业共享，任一成员占用都减少余量 |
| 担保覆盖 | `(coverageLimit − occupied − preOccupied) ÷ coverageRatio` | 仅对"担保要求=开"的产品生效；担保可支持借款金额＝剩余覆盖÷覆盖比例 |

- 冻结：任一层冻结时该授信新增提款可用额度为 0；已占用可以因还款减少（冻结不减占用、不碍恢复）。
- 预占/实占/释放**逐层记账**：台账流水（LimitRecord）带 `layer` 字段（TOTAL/PRODUCT/GROUP/GUARANTEE），同一次业务动作在各层各留一条，保证"金额、状态、业务记录可相互核对"。
- 降额：新上限低于当前占用时，保留实际占用与已有债务，可用额度按下限 0 处理并标记 `restricted`，只限制新增提款，不影响存量借据还款。

## 2. 授信申请与调整流程

```text
客户提交 → 渠道准入校验 → 中台建立授信申请单(CR-) → 模拟审批（同步/延迟回调/不回调）
→ 审批结果（含批准额度）→ 中台生效：初次创建授信＋各层配置 / 提额 / 降额（保留占用）
```

- 申请类型 `type`：`INITIAL`（初次）/ `LIMIT_INCREASE`（提额）/ `LIMIT_DECREASE`（降额）/ `RENEWAL`（续授信）。冻结/解冻不走审批，是中台运营操作。
- 审批结果只回"批准额度"与结论；各层配置（产品子额度、集团归属、担保覆盖）随申请单提交、审批通过后一并生效。

### 渠道 → 中台

`POST {middle}/middle/api/v1/credit/applications`

```json
{ "customerName": "企业甲", "type": "INITIAL", "requestedLimit": 800000.00,
  "groupNo": "G-202609001",
  "productSubLimits": [ { "productId": "LOAN-PURCHASE", "subLimit": 700000.00 } ],
  "guaranteeCoverage": { "orgName": "担保机构丙", "coverageLimit": 400000.00, "coverageRatio": 0.8 } }
响应 202 { "bizOrderNo": "CR-202609060001", "status": "PROCESSING" }
```

`GET {middle}/middle/api/v1/credit/applications/{bizOrderNo}` → `{ status: PROCESSING|APPROVED|REJECTED, approvedLimit, creditId }`

### 中台运营操作（冻结/解冻/额度查询）

- `POST {middle}/middle/api/v1/credit/{creditId}/freeze`、`POST .../unfreeze`：body `{ "reason": "..." }`。
- `GET {middle}/middle/api/v1/credit/{creditId}/limits?productId=LOAN-PURCHASE` → 各层余量与最终可用：

```json
{ "creditId": "CR-...", "frozen": false, "restricted": false,
  "layers": {
    "TOTAL":     { "limit": 800000.00, "occupied": 0, "preOccupied": 0, "remaining": 800000.00 },
    "PRODUCT":   { "productId": "LOAN-PURCHASE", "limit": 700000.00, "remaining": 700000.00 },
    "GROUP":     { "groupNo": "G-202609001", "limit": 600000.00, "remaining": 600000.00 },
    "GUARANTEE": { "coverageLimit": 400000.00, "coverageRatio": 0.8, "remaining": 400000.00, "supportable": 500000.00 } },
  "available": 500000.00 }
```

### 阶段 2 接口变更

- `GET /middle/api/v1/drawdowns/options` 的 `availableAmount` 改为多层最小值。
- 报价/申请校验改用多层可用额度；预占/释放逐层执行（对渠道透明，契约字段不变）。

## 3. 模拟服务审批接口

| 操作 | 端点 | 说明 |
| --- | --- | --- |
| 提交审批 | `POST /sim/api/v1/approvals` | `{ "bizOrderNo", "customerName", "requestedLimit" }`；幂等同付款 |
| 查审批 | `GET /sim/api/v1/approvals/{extSerialNo}` | 返回 `status`＋`result`（APPROVED/REJECTED）＋`approvedLimit` |
| 回调 | `POST {middle}/middle/api/v1/callbacks/external-result` | `type: "APPROVAL"`，`result: APPROVED/REJECTED`，`approvedLimit` |

审批复用 §2 阶段 2 的五种场景配置（SYNC_SUCCESS 等）；`approvedLimit` 可能小于 `requestedLimit`（模拟"批准额度低于申请"的调查点）。

## 4. 版本快照

- **中台产品配置**：每次修改写入不可变版本行 `ProductConfigVersion`（versionId、各规则字段、生效时间）；报价快照绑定 `productVersionId`，**申请校验按报价绑定的版本执行，不用当前配置**（新配置只适用于新报价）。
- **渠道开放规则**：渠道在生成申请单时把命中的规则快照（金额上限、期限、开关）存入 `ChannelApplicationRecord.channelRuleSnapshotJson`，后续争议按快照核对。
- 台账流水、报价快照、借据创建参数均携带版本号，构成"合同快照按约定版本执行"的证据链。
