# 事实分层与一致性检查复验（2026-10-31）

## 结论

已在 LangChain 运行时接入可选的 `BUSINESS_CODE_AGENT_ANSWER_MODE=facts`，包含分层事实协议、实际交付原文的引用表、引用与字段分段检查、有限的一致性规则及程序答案组装。**真实复验未通过默认启用验收，默认仍为 plain。**

两次新回答没有重复上一轮“当前渠道接口不能直接区分”的总断言，说明提示与答题格式有局部变化；但文件版遗漏透传字段的生产端引用，校验输出大量未确认；混合版回答了中台字段，没有完整确认渠道响应，而且把渠道后端行为标成页面使用。不能把表述改变等同于回答完整正确。同日[轨迹复盘](agent-trace-review-20261031.md)进一步指出“直接支持”存在接口数据与页面体验的歧义，不能只凭该标题判错，应复核页面字段使用、前端收益保证等具体断言的依据；原始模型结果和旧复核记录保留。

这次暴露了本方案自身的缺口：模型生成资源 ID、决定字段归属和事实层次，程序只检查引用与声明范围，仍会继承模型的错误分类。字段分段均出现在代码中也不能证明完整路径或跨系统绑定。后续需要先约束返回对象身份与透传连接，再判断字段可用性；单靠增加事实标签不能消除这些不确定性。

本记录由助手依据源码复核，`humanReviewed=false`。这是已知开发回归的单题验证，不是新保留题、人工验收或业务链路完整性证明。

## 实现

调查仍由 `create_agent` 调用 Read／Glob／Grep 和可选 SearchCode。事实模式保留最后一次无工具模型调用，输入当前问题、必要历史和实际交付的 Read／SearchCode 原文，不输入搜索命中列表、旧模型草稿或参考答案作为实现证据。

模型输出资源、事实、引用、分层答案、建议和缺口。程序核对：

- 引用的文件和行号确实出现在本轮原文；若提供引文，须逐字属于引用范围。同一文件分次交付的原文可共同引用，不从磁盘额外补入未交付行。
- 当前实现事实引用源码，需求与导航不能代替实现。声明的事实类型必须与声明的资源层次一致；此检查不保证模型声明的层次本身正确。
- 返回路径各分段、映射字段及输入／输出字面值出现在所引原文中。该检查不推导数据流、嵌套或跨方法绑定。
- 数据可用性使用同一声明对象下所有通过检查的返回字段，不允许通过遗漏事实 ID 隐藏已经观察到的字段。缺少依据输出未确认，不推出不存在。
- 建议新增的字段如已观察到返回，提示先复用。建议列出的依据必须全部通过引用／范围检查，不能丢弃失败项后继续作出建议。
- 模型的 `ui` 标签与代码引用不直接证明页面消费关系；当前这一关系保留为未确认。其他业务语义只作为“原文解读”，不标为程序证明。

检查结果和原始结构输出随运行的 `usage.verification` 保存；`semanticProof=false`。格式失败不放行自由文本，也不增加调用重试。检查本身不调用模型。plain 与 facts 的会话上下文分开核对。

## 源码依据与逐版问题

当前源码与冻结原文在以下关键内容一致：

- `ChannelService.java:127-136` 查询中台详情，并把完整 `middleDetail` 放在响应的 `detail` 中，同时返回 `middleStatus` 与 `displayStatus`。
- `DrawdownService.java:257-265` 的详情对象包含 `payments[].status` 和 `booking.status`。
- `ChannelService.java:195-203` 把中台多个非最终状态归为 `PROCESSING`。

因此完整渠道响应已有 `detail.payments[].status` 与 `detail.booking.status`；仅看 `displayStatus` 不能细分这些状态。页面是否使用它们要另查。`TO_BOOK` 表示待入账，不能直接解释为入账失败；`RETRY_NEEDED` 才体现失败后的重试需要。

文件版模型已给出“渠道响应透传了所需字段”的判断，但：

- `detail.booking.status` 与 `detail.payments[].status` 只引用渠道返回行，没有同时引用对象生产端；程序无法确认完整路径。
- `payments[].status` 的中台引用只选了 262 行，遗漏 261 行的 `payments` 键。
- 映射事实使用了自由说明句作为 output，而不是源码的字面值；来源 ID 还指向同文件另一读取块。
- 初版程序在部分建议依据失败后仍保留其余依据并展示建议，导致不够可靠的改法继续流出。这是校验实现的问题，已在本地修复。

混合版模型正确抽出中台 `status`、`payments[].status` 与 `booking.status`，但没有把该对象经渠道透传的连接作为同一条字段事实。它把渠道后端的响应构造标为 `ui`，原程序检查了引用存在，却没能识别其层次错误。映射输出仍是说明句，另有业务约定当实现、需求事实挂到业务资源的问题。初版程序输出不能当成渠道与页面能力已获确认。

## 真实复验后的本地修正

修复同文件分块引用、建议依据不完整仍放行、ui 标签误当页面使用证明，以及检查状态的表达。修复后只重放**已保存的模型结构输出**，模型调用数为 0，未重写两次真实响应记录。

本地重检查仍不能补齐文件版缺失的透传生产端引用，也不能把混合版中台字段自动归到渠道对象。它能拦下未完整支撑的建议和页面使用断言，不能宣称已答对原题。后端相关 77 项测试通过，覆盖这些实际问题、原文引用、冻结提示一致性、调用预算、提前草稿不能绕过事实流程、上下文、取消、工程隔离和本机模拟兼容接口。保留既有 HTTPError 清理提示。本轮无前端改动或页面交互验收。

下一步应以实际文件／方法为对象锚点，把“谁返回、透传给谁、字段由哪里产生”分别记录。来自另一个接口的字段不能自动算作本题接口字段；缺失连接应成为预算内的补查任务。完成这一约束后，需要新的固定证据验证，再验证允许继续搜索的完整 Agent。当前不把实验切为默认，也不把检索或资料不足当成这次错误的唯一原因。
