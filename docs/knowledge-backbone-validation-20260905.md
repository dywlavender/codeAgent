# 当前知识主干核查与真实模型对照

日期：2026-09-05。依据：[项目整改指导方向](knowledge-backbone-direction.md)。

本文保留改写前的内容快照和实验结论。后续变更与同题复测见 [两层主干改写报告](knowledge-backbone-rewrite-20260905.md)，不覆盖下文历史数据。

## 结论

当前主干仅部分符合定义，结构化图谱更未形成有效关系地图。真实模型对照也没有证明当前主干能稳定减少调查成本：可选主干组 7/8 次实际取得基线内容，平均耗时与工具调用仍未改善；直接注入同一份内容后，少量检查点更好，但总体耗时和调用数没有优势。

不能把结果解释成“完全没有任何作用”：直接注入确实改变了部分题目的检索起点。也不能把这一变化直接当成“少走了弯路”：整体调查与回答的收益尚未得到证明。

因此，用户“当前有和没有差不多”的观察得到本轮支持。本文没有验证一份更完整主干的收益，更没有验证结构化关系相对于同内容 Markdown 的额外价值；这些仍是待验证假设。

## 内容与实现核查

当前配置实际使用 `knowledge/baseline/withdraw-flow.md`，仅这一份文件、21 行。三个代码仓库是 `examples/channel-h5`、`examples/channel-service`、`examples/loan-middle`，未配置额外需求资料。本次没有更换或扩写基线，也没有构造一份更有利于实验组的资料。

| 定义要求 | 当前内容 | 判断 |
| --- | --- | --- |
| 项目整体认识与系统职责 | H5 发起、渠道转发、中台提供接口 | 部分符合，已有粗粒度系统地图 |

| 术语、别名与代码词的对应 | 普通业务词，无显式别名或代码代号对应 | 缺少能改善检索词的知识；当前示例命名直白，本身也没有明显的术语歧义 |

| 持续调查与覆盖参照 | 可以对照九个业务步骤 | 未标记业务边界、未覆盖环节或当前示例实现性质，不足以作为全流程完成度的可靠参照 |

## 预先确定的测试方法

- 4 题：流程与职责、优惠券跨系统调用链、合同／授权前置校验、受理后的放款与通知边界。
- 3 组：代码与原 README；加原样基线且可选读取；相同资料另将基线原文直接注入上下文。
- 每题每组各 2 次，共 24 次真实模型调用。直接注入组仅用于区分“没有读到”与“内容没有增益”，不是当前生产接入方式，也不证明模型实际依赖了注入内容。
- 每次使用独立临时工作区和新会话，保留三个仓库的原 README，关闭 MCP 与技能，不使用历史回答或生产数据库；读取工具与目录规则沿用当前运行时。
- 在第一次调用前保存问题、每题 5 项事实检查点、运行顺序和输入资料快照；组内顺序按固定随机种子排列，两路并发，每次 240 秒超时、CLI 计价预算上限 1 美元。
- 答案由本次执行助手逐项对照源码复核，并记录前后矛盾或无依据的断言。不是模型自动打分，也没有独立业务专家盲评。
- 观察内容覆盖、错误结论、实际工具轨迹、基线读取、关键文件定位、耗时与调用数；不以进程 `completed` 或读取过基线直接判定回答正确或主干有用。

首轮沙箱内调用停在启动阶段，未得到可用答案，随后停止该批进程。联网重跑最初被自动审批拒绝；核实仅使用演示资料和用户已有本机模型网关后，重跑获准。启动异常批次单独保留，不计入效果统计。

正式首批 24 次中，有 3 次被本次新增的模型元信息采集代码中断：字符串格式的 `message` 被当作对象处理。这是测试采集错误，不计为模型答错。修正类型判断后，对受影响的“前置条件第 1 次、业务边界第 1 次、业务边界第 2 次”各三组整组补测，共 9 次；补测决定在执行前保存在 `supplement-plan.json`。主比较使用补测后的完整 24 个结果，同时保留首批结果及其余 5 个完整三组组合的统计，不挑选每组较好的答案。

本地 CLI 版本为 2.1.237，使用用户现有的 `127.0.0.1` 模型网关。采集到的初始化模型标识为 `claude-opus-4-8[1m]`，回答消息标识为 `glm-5.3`，两者不同；未核验网关上游真实模型。这里评估的是当前本地 Claude Code 调用链的行为，不能宣传为某个确定 Claude 模型的效果。

## 对照结果

主比较共 24 次，每组 8 次，均返回实质答案。原始首批 24 次加整组补测 9 次，共执行 33 次正式调用，其中 3 次采集异常、6 次成功答案因整组补测而只保留作原始记录。启动异常批次不在这些数字内。

| 指标 | 无主干，保留 README | 当前可选主干 | 同一主干直接注入 |
| --- | ---: | ---: | ---: |
| 实质答案 | 8/8 | 8/8 | 8/8 |
| 平均耗时 | 35.35 秒 | 36.84 秒 | 36.35 秒 |
| 耗时中位数 | 32.86 秒 | 36.66 秒 | 35.89 秒 |
| 工具调用总数 | 96 | 109 | 96 |
| 工具错误总数 | 0 | 2 | 0 |
| 预定事实检查点满足数 | 35/40 | 33/40 | 37/40 |
| 工具实际取得基线正文或片段 | 不提供 | 7/8 次 | 0 次，8/8 已注入上下文 |

检查点满足数不是答案正确率。每题五项检查无法穷尽答案中的附带错误，逐次复核另记了额外断言和矛盾。直接注入比无主干多满足两项，但样本很小、每题仅两次且由同一执行助手复核，不能据此宣称稳定提升；可选主干也不能据此宣称稳定变差。

可选主干的两次工具错误都发生在补测的第一轮业务边界题，分别为模型拼错临时路径和搜索未授权的共同上级目录。之后恢复调查并产生答案，错误调用保留计数；它们是当前运行行为的一部分，但没有证据表明由主干内容导致。

## 实际改变了什么，又没有改变什么

### 1. 部分入口定位改变了，但没有带来稳定的整体节省

直接注入组的两次流程题、两次前置条件题，都以搜索 `WithdrawApply.vue`、`ChannelWithdrawController`、`MiddleWithdrawController` 开始。这与基线给出的入口一致，说明这类信息可以影响检索起点。

但是，无主干组也能通过“提款／withdraw”等业务词迅速定位这些小仓库。以第二次流程题为例，首次取得 H5 内容的工具序号从无主干的第 6 次变为直接注入的第 4 次，但总调用从 10 次变为 13 次。因此不能用某一步提前就证明整轮少走弯路。

### 2. 有些基线是在源码调查之后才被使用

可选主干组第一轮优惠券题在第 9 次工具调用取得 `WithdrawQueryService` 内容后，第 10、11 次才查基线；两次前置条件题都在最后的第 15 次工具调用取得基线内容。

这些记录支持“基线被用于补充业务说明”，没有证据表明它指导了前面的代码定位。第二次优惠券题没有访问基线，仍正确识别最终实现返回固定列表、没有金额筛选。

“取得基线内容”同时统计成功的 Read 和返回正文的 Grep，不把 Glob 或只返回文件名的搜索算作内容读取。

### 3. 业务描述与实现事实仍会混淆

- 流程题：无主干与可选主干的四个答案都出现“字段非空意味着合同／授权必须已完成”的表述，部分随后又承认前端硬编码，形成矛盾；直接注入第一轮也出现该错误，第二轮对真实性的区分更清楚。
- 前置条件题：三组都识别前端固定 ID、后端未核验真实业务状态；但主比较的六个答案都漏掉另一组银行卡、还款方式、还款日非 null 检查，部分还误称两项 ID 是全部校验条件。
- 优惠券题：三组都识别中台固定返回，但可选主干第二轮臆定金额单位为元、漏写中台完整接口路径；直接注入第二轮把代码固定金额描述成用户选择的金额。
- 业务边界题：三组都发现当前项目没有实际放款和结果通知实现，但无主干与可选主干第二轮仍无依据地把职责归到下游系统；直接注入第二轮没有做这个归属断言，却误称 Feign 客户端只有申请一个写接口，实际另有签约、授权。

基线的存在、读取甚至直接注入，均不足以保证模型准确区分业务约定与代码实现。本轮差异必须连同这些错误一起呈现，不能只展示有利案例。

## 对整改的含义

1. 当前应先解决可观察的缺口：原文九步流程及三个入口没有完整进入结构化结果，图谱没有关系；定位原因时应保留原文与导入结果的逐项对照。
2. 内容要明确业务范围、术语对应、职责及有来源的关系，尤其区分申请受理与后续放款。已有信息足以写清的边界可以补齐，不存在的业务不能编造。
3. 查询整改要证明这些知识实际帮助了整体理解和持续调查。仅把当前21行强制塞入上下文，本轮没有显示总体效率优势，不应直接作为确定方案上线。
4. 当前示例已经容易检索，收益弱就是实际结果。若后续测试真实复杂问题，必须说明是新的验证范围，保留现有普通题作对照，不能重写本轮结论。
5. 内容收益与结构化收益分别验证。如果同内容的普通文档已足够，就需要重新评估关系结构及维护成本；增加图谱节点数量不构成验收标准。

本次没有修改业务基线、问答生产逻辑或生产数据库，只新增评测脚本、结果资料和本文。
