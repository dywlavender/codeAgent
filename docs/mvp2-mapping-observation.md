# 旧版 MVP2：问答驱动的 Mapping（兼容说明）

本文件描述的是早期 MVP2 的实验能力。当前主流程已经收敛为：

```text
业务知识 + 项目上下文 + 人工维护的入口锚点
        ↓
Query Agent 运行时解析入口并检索代码证据
        ↓
回答只引用可验证的业务 / 代码 / 需求 Evidence
```

## 当前结论

新建或维护业务知识时，优先在业务基线 Markdown 的 `### 调查入口` 小节补充少量入口锚点。锚点只保存：业务对象、应用、入口类型和入口名称，不保存文件、类、方法或行号。代码索引更新后，Query Agent 会按应用作用域解析入口名称；解析不到或出现歧义时自动退回全局代码检索。

因此，问答过程不会自动写入 `business_code_mapping`，也不会产生需要管理员逐条确认的 Mapping 提案。入口锚点不会在查询时自动学习，避免把一次回答中的推测长期写入知识库。

## 历史数据与接口

以下表和接口仍保留，用于兼容已有数据库、迁移和显式历史管理操作：

```text
business_code_mapping_observation
business_code_mapping
```

```http
GET /api/knowledge/mapping-observations?status=CANDIDATE
POST /api/knowledge/mapping-observations/{id}/accept
POST /api/knowledge/mapping-observations/{id}/reject
```

它们不属于当前默认查询链路。新代码不应依赖这些接口来获得业务—代码关联；如需清理历史数据，应先完成数据备份并单独制定迁移方案。

## 为什么收敛

老项目的代码命名、模块边界和业务理解差异较大，自动生成完整 Mapping 容易把不确定判断固化为长期知识。入口锚点把人工需要确认的内容压缩到“这个业务在这个应用里的入口叫什么”，其余文件、方法、调用链和行号交给可重建的代码索引按运行时事实解析。

## 验收重点

当前验收关注以下行为：

- 有效锚点能在同一应用内解析为代码候选，并减少无关的全局检索；
- 锚点过期、缺失或同名冲突时会退回全局检索，不阻断回答；
- 同名入口必须按应用隔离；
- 代码重构只需要重新索引，不应改变业务知识或自动新增业务 Mapping；
- 查询和回答不会污染业务知识、入口锚点或历史 Mapping 表。
